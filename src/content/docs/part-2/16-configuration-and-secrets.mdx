The same container image should run on your laptop, in CI, in staging and in production. What changes between them, from database URLs to feature flags to API keys, is configuration. This chapter sets one pattern for all five stacks: layered sources, a typed configuration object validated at startup, and secrets that never touch the repository.

## Layers

Every stack in this book merges configuration from several sources, later ones winning:

1. **Defaults in code or a committed file** (`appsettings.json`, `application.yml`, a settings module). Safe, non-secret values only.
2. **Environment-specific files** for local development (`appsettings.Development.json`, `application-local.yml`, a `.env` that is **not** committed).
3. **Environment variables**, set by the platform: Kubernetes, your PaaS, CI.
4. **A secret store** (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, Vault), usually surfaced to the process as environment variables or mounted files.

Environment variable naming follows each stack’s convention for nested keys: `Shelfwise__Loans__MaxPerMember` in .NET (double underscore), `SHELFWISE_LOANS_MAXPERMEMBER` in Spring (relaxed binding), plain upper-case names elsewhere.

## Typed, validated, at startup

Reading `process.env.LOAN_DAYS` in the middle of a service is how configuration bugs reach production: a typo returns `undefined`, a string is compared to a number, nobody notices until a code path runs. Instead, bind all settings into **one typed object at startup**, validate it, and refuse to start if it is wrong.

```ts
const Env = z.object({
  DATABASE_URL: z.string().url(),
  LOAN_DAYS: z.coerce.number().int().min(1).max(60).default(21),
  MAX_LOANS_PER_MEMBER: z.coerce.number().int().min(1).default(5),
});
export type Env = z.infer<typeof Env>;

ConfigModule.forRoot({ isGlobal: true, validate: (raw) => Env.parse(raw) }); // throws at boot
```
</Stack>

<Stack id="java" lib="@ConfigurationProperties">
```java
@Validated
@ConfigurationProperties("shelfwise.loans")
public record LoanProperties(
    @Min(1) @Max(60) int loanDays,
    @Min(1) @Max(50) int maxPerMember) {}

// application.yml: shelfwise.loans.loan-days: 21
// Enable with @ConfigurationPropertiesScan; invalid values stop the context from starting.
```
</Stack>
<Stack id="go" lib="explicit">
```go
type Config struct {
	DatabaseURL       string
	LoanDays          int
	MaxLoansPerMember int
}

func Load() (Config, error) {
	c := Config{DatabaseURL: os.Getenv("DATABASE_URL"), LoanDays: 21, MaxLoansPerMember: 5}
	if c.DatabaseURL == "" {
		return c, errors.New("DATABASE_URL is required")
	}
	if v, ok := os.LookupEnv("LOAN_DAYS"); ok {
		n, err := strconv.Atoi(v)
		if err != nil || n < 1 || n > 60 {
			return c, fmt.Errorf("LOAN_DAYS must be 1–60, got %q", v)
		}
		c.LoanDays = n
	}
	return c, nil // main() exits with the error if any
}
```
</Stack>

```python
class Settings(BaseSettings):
```

The pattern is identical in all five: **one object, typed, validated, created once at startup, injected where needed**. Tests build that object directly with test values, with no environment juggling.

## Secrets

A secret is configuration that would hurt if it leaked: database passwords, API keys, signing keys. Four rules cover most of the risk:

1. **Never commit secrets.** Commit a `.env.example` with names and dummy values; add `.env` to `.gitignore`; enable secret scanning in the repository.
2. **Store them in a secret manager**, and give each service read access to its own secrets only.
3. **Inject at run time**, as environment variables or mounted files, never baked into an image.
4. **Make rotation routine.** If changing a password needs a code change or a long outage, it will not be rotated.

<Pitfall title="Secrets in logs">
Logging the whole configuration object at startup is useful for debugging and a classic leak, because logs are shipped to systems with much wider access than the secret store. Mark secret fields so they are redacted (`SecretStr` in Pydantic, a custom `ToString` in C#, a `String()` method in Go), or log only non-secret keys.
</Pitfall>

<FromTS>
`dotenv` is fine for local development, but in production the platform sets real environment variables and the `.env` file should not exist. All five stacks here can read `.env` files locally (natively or through a small library) with the same rule: never in the image, never in Git.
</FromTS>

## Feature flags

A feature flag is configuration that turns behaviour on and off without a deploy. Simple flags can be settings like the ones above; once you need per-user rollout, percentages or instant changes, use a flag service (LaunchDarkly, Unleash, OpenFeature-compatible providers). Treat flags as temporary: each one gets an owner and a removal date, or the codebase fills with dead branches.

<InTheWild>
In Kubernetes, configuration usually arrives through a ConfigMap (non-secret) and a Secret (secret), both exposed as environment variables or files, often synced from a cloud secret manager by an operator. The application never knows; it reads its environment. That separation is what lets one image move unchanged from staging to production.
</InTheWild>

<InterviewLens>
"How do you manage configuration and secrets across environments?" A strong answer: one build artefact, configuration from the environment with committed safe defaults, a typed and validated settings object that fails fast, secrets in a manager with per-service access and rotation, nothing secret in Git, images or logs, and secret scanning in CI.
</InterviewLens>

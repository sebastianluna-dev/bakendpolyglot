Every stack offers three ways to talk to a database: a full **ORM** that maps rows to objects, a **query builder** that composes SQL with types, and **raw SQL** with a thin mapping layer. Each has good uses, and all of them let you write the same performance bug. This chapter compares them, fixes that bug in five stacks, and covers the two operational pieces that every service needs: migrations and connection pools.

## Three levels of abstraction

| Stack | ORM | Query builder or SQL-first | Raw SQL |
| --- | --- | --- | --- |
| TypeScript | Prisma, TypeORM | Drizzle, Kysely | `pg` |
| C# | Entity Framework Core | — | Dapper |
| Java / Kotlin | Spring Data JPA (Hibernate) | jOOQ | `JdbcClient` |
| Go | GORM | `sqlc` (generates Go from SQL) | `pgx` |
| Python | Django ORM, SQLAlchemy ORM | SQLAlchemy Core | `asyncpg`, `psycopg` |

An **ORM** gives you objects, relationships, change tracking and migrations; it is fastest for CRUD and slowest to debug when the generated SQL is wrong. A **query builder** or SQL-first tool keeps you close to SQL with type safety; it suits read-heavy, query-shaped code. **Raw SQL** is unbeatable for reports and tuned queries. Mature codebases mix them: ORM for writes and simple reads, SQL for the queries that matter.

## The N+1 problem

The most common database performance bug looks innocent. List a member’s open loans, then show each loan’s book title:

```ts
const loans = await db.loan.findMany({ where: { memberId, returnedAt: null } }); // 1 query
for (const loan of loans) {
  const copy = await db.copy.findUnique({ where: { id: loan.copyId } });         // N queries
  const book = await db.book.findUnique({ where: { id: copy!.bookId } });        // N more
}
```

Fifty loans become 101 round trips. On a laptop it takes 40 ms and nobody notices; in production, with a database 1 ms away and real traffic, the page takes a second and the database is busy for nothing. ORMs make it worse with **lazy loading**: touching `loan.copy.book.title` in a template silently runs a query.

The fix is the same in every stack: say up front what you need, and let the tool fetch it in one query (a join) or one extra query per relation (a batched `IN (…)`).

```python
loans = (
    Loan.objects
    .filter(member_id=member_id, returned_at__isnull=True)

    .order_by("due_at")

```

Two patterns are visible. EF Core and JPA **project** into a small read model (`OpenLoan`) instead of loading full entities, which also avoids change-tracking overhead. Prisma and Django **eager-load** the relations. Go’s `sqlc` sidesteps the question: you write the join, and it generates the typed function.

<Pitfall title="Find N+1 before production does">
Turn on SQL logging in development and read it when a page feels slow. Better, make it fail tests: Django has `assertNumQueries`, Hibernate can log statement counts per request, and in every stack you can count queries in an integration test for the endpoints that list things.
</Pitfall>

## Migrations

The schema changes with the code, so its changes are versioned with the code. A **migration** is an ordered script; a tool records which ones each database has applied and runs the rest.

| Stack | Tool | Generated from models? |
| --- | --- | --- |
| TypeScript | Prisma Migrate, Drizzle Kit | Yes |
| C# | EF Core migrations | Yes |
| Java / Kotlin | Flyway or Liquibase | No: you write SQL |
| Go | goose, golang-migrate, Atlas | No (Atlas can diff) |
| Python | Django migrations, Alembic | Yes (autogenerate) |

Generated migrations are a starting point, not a final answer: always read the SQL before committing. Two rules keep deployments safe. First, never edit a migration that has run anywhere shared; add a new one. Second, make schema changes **backward compatible** with the code still running: add a nullable column, deploy code that writes it, backfill, then make it required. Renaming a column in one step breaks every instance still running the old code during a rolling deploy.

## Connection pools

Opening a database connection costs a TCP and TLS handshake plus authentication, several milliseconds. A **pool** keeps connections open and lends them out per query or transaction. Every stack has one built in or one standard choice: HikariCP in Spring (default size 10), Npgsql’s pool in .NET, `pgxpool` in Go, Prisma’s and SQLAlchemy’s pools, Django’s persistent connections.

Pools need sizing from the database down, not from the service up. PostgreSQL handles a limited number of connections well (each one is a process), so the total across **all replicas** must fit:

```text
replicas × pool size per replica  ≤  database max_connections − headroom
8 × 10 = 80                       ≤  100 − 20      ✓
8 × 20 = 160                      ≤  100 − 20      ✗
```

A bigger pool is rarely faster: past roughly a few connections per database CPU core, queries just wait inside Postgres instead of in your pool. When you need many replicas, put **PgBouncer** (or a managed equivalent) in front of the database.

<InTheWild>
Teams argue about ORMs forever. The pragmatic consensus in most companies: use the stack’s mainstream ORM for writes and straightforward reads, drop to SQL for anything performance-sensitive, and review generated SQL in code review for the endpoints that list things. Go teams lean SQL-first with `sqlc` more than any other community.
</InTheWild>

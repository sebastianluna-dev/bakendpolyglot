Tests are how a team changes code without fear. For a backend, the interesting bugs live where pieces meet: SQL that does not do what the ORM call suggested, a constraint that fires, a status code mapped wrong. This chapter sets the testing strategy used by every companion app: unit tests for pure logic, integration tests against a **real** PostgreSQL started by Testcontainers, and a thin layer of API tests over the whole service.

**Unit tests** cover logic with no I/O: due-date calculation, the rule that a member with three overdue loans cannot borrow, DTO mapping. They run in milliseconds, so you run them constantly.

**Integration tests** cover everything that touches the database or the HTTP layer: repository queries, constraints, transactions, and each endpoint’s status codes and bodies. This is where backend bugs are found, so in this book the integration layer is thick.

**API or end-to-end tests** run the built service with its real dependencies, usually in CI, for a handful of critical journeys: lend a copy, return it, see the history.

## A real database in every test run

Mocking the database tests your mocks. In-memory substitutes (SQLite, H2, EF Core’s in-memory provider) speak a different dialect and skip the constraints that matter, so tests pass while production fails. **Testcontainers**, available in all five stacks, starts a real PostgreSQL in Docker for the test run, in a few seconds:

Start one container per test run (not per test), and isolate tests from each other by wrapping each one in a transaction that is rolled back, or by truncating tables between tests. Both are fast; pick one per project.

## Determinism

A test that sometimes fails is worse than no test, because people learn to ignore red builds. The usual causes, and their fixes:

- **Time.** Code that calls `now()` directly cannot be tested at month ends or across time zones. Inject a clock: `TimeProvider` in .NET, `java.time.Clock`, a `func() time.Time` in Go, a `now` dependency in Python and Nest. Shelfwise tests lend a book "on 31 January" and check the due date.
- **Randomness and ids.** Inject the generator, or assert on shape instead of exact values.
- **Order.** Tests that depend on running after another test break when run alone or in parallel. Each test creates its own data.
- **External services.** Never call a real third-party API in a test. Use a fake server (WireMock, `httptest`, MSW, `respx`) with recorded responses.

<Pitfall title="Over-mocking">
A unit test that mocks five collaborators and asserts the exact calls made to each one breaks on every refactor and proves little. Prefer real objects for in-process collaborators, fakes for I/O boundaries, and mocks only when the interaction itself is the behaviour, such as "an email was sent".
</Pitfall>

## What to test in an endpoint

For each endpoint, the integration suite checks the contract, not the implementation:

1. The success status, headers (`Location`, `ETag`) and body shape.
2. Each documented error: 404, 409, 412, 422 with the Problem Details body.
3. The database effect: the row exists, the loan is closed, the version moved.
4. Authorization, once it exists (Part III).

Because Shelfwise has one OpenAPI contract and eight implementations, the API-level suite is written once, in a language-neutral runner, and executed against every stack in CI. That is the gate for Phase 2.

<InTheWild>
Teams that adopt Testcontainers rarely go back: CI needs Docker, and suites take a few seconds longer to start, but entire classes of "passes locally, fails in prod" bugs disappear. Expect integration tests to be the majority of a mature backend suite, with unit tests concentrated on genuinely complex domain logic.
</InTheWild>

<InterviewLens>
"How do you test a service that depends on a database and an external payment API?" A strong answer: unit tests for domain rules with no I/O; integration tests against a real database via Testcontainers with migrations applied; a fake HTTP server for the payment API, including error and timeout cases; a few end-to-end journeys in CI; deterministic time and data; and contract tests if other teams consume the API.
</InterviewLens>

This chapter models Shelfwise in PostgreSQL, the database every app in this book uses, and covers the indexing and query-reading skills that separate senior backend engineers from everyone else.

```sql
CREATE TABLE books (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  isbn       text NOT NULL UNIQUE CHECK (isbn ~ '^97[89][0-9]{10}$'),
  title      text NOT NULL,
  author     text NOT NULL,
  year       int  CHECK (year BETWEEN 1450 AND 2100),
  version    int  NOT NULL DEFAULT 1
);

CREATE TABLE copies (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  book_id   bigint NOT NULL REFERENCES books (id),
  barcode   text   NOT NULL UNIQUE,
  status    text   NOT NULL DEFAULT 'available' CHECK (status IN ('available', 'lost', 'retired')),
  added_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE members (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email  text NOT NULL UNIQUE,
  name   text NOT NULL,
  since  date NOT NULL DEFAULT current_date
);

CREATE TABLE loans (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  copy_id      bigint NOT NULL REFERENCES copies (id),
  member_id    bigint NOT NULL REFERENCES members (id),
  loaned_at    timestamptz NOT NULL DEFAULT now(),
  due_at       timestamptz NOT NULL,
  returned_at  timestamptz,
  CHECK (due_at > loaned_at)
);

CREATE UNIQUE INDEX one_open_loan_per_copy ON loans (copy_id) WHERE returned_at IS NULL;
```

Notice how many rules live in the schema: ISBN format, valid years, allowed statuses, due dates after loan dates, and the key one, **one open loan per copy**. If two librarians lend the same copy at the same instant, one insert fails with a unique violation, whatever the application code does. Your code turns that error into a `409` (Chapter 23 covers concurrency in depth).

<Pitfall title="Rules only in application code">
A rule that lives only in an `if` statement is broken the first time two requests race, a migration script runs, or another service writes to the same table. If the database can express it (unique, foreign key, check, partial unique index), let the database enforce it, and keep the application check too for good error messages.
</Pitfall>

## Normalisation, briefly

Normalisation removes duplication so a fact lives in one place. The practical target is **third normal form**: every column depends on the key, the whole key, and nothing but the key. In Shelfwise, the title lives on `books`, not on each copy; a member’s email lives on `members`, not on each loan. Denormalise later, deliberately, for read performance, and only with a plan for keeping copies in sync.

## Indexes

An index is a separate, sorted structure that lets the database find rows without reading the whole table. PostgreSQL’s default is the **B-tree**, which serves equality, ranges, sorting and prefixes.

| Index | Serves | Example |
| --- | --- | --- |
| Single column | `WHERE author = $1` | `CREATE INDEX ON books (author)` |
| Composite | Left prefixes: `author`, or `author` + `year` | `CREATE INDEX ON books (author, year)` |
| Covering | Answers from the index alone | `CREATE INDEX ON books (author) INCLUDE (title)` |
| Partial | A subset of rows | `ON loans (member_id) WHERE returned_at IS NULL` |
| Expression | Computed values | `ON members (lower(email))` |

Primary keys and `UNIQUE` constraints create indexes automatically. **Foreign keys do not** in PostgreSQL, so `copies.book_id` and `loans.member_id` need their own indexes, or joins and deletes on the parent will scan.

Indexes are not free: each one slows every write that touches its columns and takes space. Index what your queries actually filter, join and sort on, which means you need to see what queries actually do.

## Reading a query plan

`EXPLAIN ANALYZE` runs a query and shows the plan the database chose, with real timings. This is the single most useful database skill for a backend engineer. Here is a search by author before and after adding an index (illustrative output; your numbers will differ):

```sql
EXPLAIN ANALYZE SELECT id, title FROM books WHERE author = 'Herbert';

-- Seq Scan on books  (cost=0.00..2041.00 rows=12 width=40) (actual time=0.03..14.88 rows=11 loops=1)
--   Filter: (author = 'Herbert'::text)
--   Rows Removed by Filter: 79989

CREATE INDEX books_author_idx ON books (author);

-- Index Scan using books_author_idx on books  (cost=0.42..48.61 rows=12 width=40) (actual time=0.02..0.06 rows=11 loops=1)
--   Index Cond: (author = 'Herbert'::text)
```

Read plans from the innermost node outwards. Look for **Seq Scan** on large tables with many rows removed by a filter, a big gap between estimated and actual `rows` (stale statistics: run `ANALYZE`), and **Sort** or **Hash** nodes that spill to disk.

## Joins

A join combines rows from several tables on a condition. `INNER JOIN` keeps only matching pairs; `LEFT JOIN` keeps every row on the left and fills missing matches with `NULL`. This query lists a member’s open loans with titles, the kind of query Shelfwise runs on every member page:

```sql
SELECT l.id, b.title, c.barcode, l.due_at
FROM loans l
JOIN copies c ON c.id = l.copy_id
JOIN books  b ON b.id = c.book_id
WHERE l.member_id = $1 AND l.returned_at IS NULL
ORDER BY l.due_at;
```

With the partial index on `loans (member_id) WHERE returned_at IS NULL` and the primary keys on `copies` and `books`, this stays fast with millions of historical loans.

<InTheWild>
PostgreSQL has become the default relational database for new projects in every stack in this book. Teams lean on its extras: `jsonb` for flexible attributes, partial and expression indexes, `RETURNING` on writes, and `pg_stat_statements` to find the slowest queries in production. Learn to read its plans and you can help any team, whatever their language.
</InTheWild>

<InterviewLens>
"This endpoint is slow. How do you find out why?" A strong answer: measure first (logs, traces, `pg_stat_statements`), find the slow query, run `EXPLAIN ANALYZE` on it with realistic parameters, look for sequential scans, misestimates and sorts, then fix with an index, a rewritten query or less data, and confirm with the plan and a load test. Mention the write cost of new indexes.
</InterviewLens>

An API is a promise. Once a mobile app or a partner integration depends on it, every field name and status code is hard to change. This chapter covers the decisions that are cheap now and expensive later: how resources are named, how errors look, how lists are paged, and how the contract is written down. Then we apply them to Shelfwise, whose API we will build in Chapter 18.

## Resources, not actions

REST APIs model **resources** (nouns) and use HTTP methods as the verbs. The URL names a thing; the method says what to do with it.

| Instead of | Prefer | Why |
| --- | --- | --- |
| `POST /createBook` | `POST /books` | The method already says "create" |
| `GET /getBooksByAuthor?a=…` | `GET /books?author=…` | Filtering is a query on the collection |
| `POST /books/42/delete` | `DELETE /books/42` | Proxies and clients understand DELETE |
| `POST /returnLoan` | `POST /loans/7/return` | A domain action on one resource is fine as a sub-resource |

Plural nouns, lowercase, hyphens for multi-word names, and nesting no more than one level deep (`/books/42/copies`, not `/libraries/1/books/42/copies/3/loans`). When an operation is really a process, such as returning a book, a sub-resource with `POST` is honest and readable.

## One error format for every stack

Chapter 9 showed five different 404 bodies. Clients should never care which stack answered, so every service in this book uses **Problem Details** (RFC 9457):

```json
{
  "type": "https://shelfwise.dev/problems/copy-on-loan",
  "title": "Copy is already on loan",
  "status": 409,
  "detail": "Copy C-0042 has been on loan since 2026-11-02.",
  "instance": "/loans",
  "copyId": "C-0042"
}
```

`type` is a stable identifier clients can switch on; `title` is a short human summary; `detail` explains this occurrence; extra members (here `copyId`) carry data. For validation errors we add an `errors` member listing each field (Chapter 13).

<Pitfall title="Leaking internals in errors">
Stack traces, SQL fragments and exception class names in a 500 response help attackers more than users. Log the details with the request id; return a generic `detail` and the id so support can find the log line.
</Pitfall>

**Offset** pagination is simple and lets users jump to page 37, which admin screens like. **Cursor** (keyset) pagination encodes the sort key of the last item in an opaque token; the next query starts right after it, using the index, at the same speed on page 1 and page 10,000, and inserts do not shift items between pages. Public APIs and infinite scroll should use cursors. Shelfwise uses this shape:

```json
{
  "items": [ { "id": 13, "title": "Dune" }, "…" ],
  "nextCursor": "eyJ0aXRsZSI6IkR1bmUiLCJpZCI6MTN9",
  "limit": 20
}
```

The cursor is base64-encoded JSON of the sort key and the id (the id breaks ties). Clients must treat it as opaque, so you can change its contents later.

## Filtering, sorting and partial responses

Use query parameters for all three: `GET /books?author=Herbert&sort=-year&fields=id,title`. Whitelist the fields that may be filtered and sorted, because each one needs an index (Chapter 14) and an unindexed sort on a large table is an outage waiting to happen.

## Versioning and change

Most changes should not need a new version. **Additive** changes (new optional fields, new endpoints, new optional parameters) are safe if clients ignore unknown fields, which you should require in your API guidelines. **Breaking** changes (renames, removed fields, new required inputs, type changes) need a new version, and the common, boring choice is a URL prefix: `/v1/books`, `/v2/books`. Header-based versioning is cleaner in theory and harder to debug in practice.

## The contract: OpenAPI

Write the API down as an **OpenAPI** document. There are two workflows:

- **Code-first**: annotations or types generate the document (NestJS Swagger, ASP.NET Core OpenAPI, springdoc, FastAPI built in, Huma or swag in Go). Fast, and the document never drifts from the code.
- **Contract-first**: write the YAML, review it like code, then generate server stubs and clients. Slower to start, better when several teams or stacks implement the same contract.

Shelfwise is a contract-first API: one `openapi.yaml`, eight implementations, and a CI job that checks each one against it.

## The Shelfwise API

| Method and path | Purpose | Success | Notable errors |
| --- | --- | --- | --- |
| `GET /books?q=&after=&limit=` | Search the catalog | 200, paged | 400 bad cursor |
| `POST /books` | Add a book | 201 + Location | 409 duplicate ISBN, 422 invalid |
| `GET /books/{id}` | One book, with ETag | 200 / 304 | 404 |
| `PATCH /books/{id}` | Edit a book, with If-Match | 200 | 404, 412, 422 |
| `POST /books/{id}/copies` | Add a physical copy | 201 | 404, 409 duplicate barcode |
| `POST /loans` | Lend a copy to a member | 201 | 404, 409 copy on loan, 422 |
| `POST /loans/{id}/return` | Return a copy | 200 | 404, 409 already returned |
| `GET /members/{id}/loans` | A member’s loans | 200, paged | 404 |
| `GET /health` | Liveness | 200 | — |

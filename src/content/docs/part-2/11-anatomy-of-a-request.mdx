The stops are the same in every stack; the names are not. Once you can map them, any framework’s documentation becomes easy to read.

## Choosing the right stop

The table is also a placement guide. A concern belongs at the **earliest** stop that has the information it needs:

- **Request ids, access logs, CORS, compression**: middleware. They do not care which route matched.
- **Authentication**: middleware, because it only reads headers. **Authorization**: a policy stop, because it often needs the route or the resource.
- **Parsing and validation**: binding. The handler should receive valid, typed data or not run at all.
- **Business rules**: the handler and the services it calls. Nothing above should know about loans or books.
- **Translating exceptions to HTTP**: the error stop, in one place per application.

<Pitfall title="Business logic in middleware">
Middleware that loads a book, checks its status and rejects the request works, until a second endpoint needs a slightly different rule and nobody remembers the middleware exists. Keep middleware generic; anything that knows your domain belongs in a handler or a service it calls.
</Pitfall>

## Your first middleware, five times

A request id is the classic first middleware: accept one from the caller (so it can be followed across services), generate one otherwise, return it in the response, and attach it to every log line.

<FiveStacks note="Read or create X-Request-Id, echo it, log with it">
<Stack id="express" lib="Express">
```ts
import { randomUUID } from 'node:crypto';

app.use((req, res, next) => {
  const id = req.get('x-request-id') ?? randomUUID();
  res.setHeader('x-request-id', id);
  req.log = logger.child({ requestId: id });   // pino child logger
  next();
});
```
</Stack>
<Stack id="cs" lib="ASP.NET Core">
```csharp
app.Use(async (ctx, next) =>
{
    var id = ctx.Request.Headers["X-Request-Id"].FirstOrDefault() ?? Guid.NewGuid().ToString();
    ctx.Response.Headers["X-Request-Id"] = id;
    using (app.Logger.BeginScope(new Dictionary<string, object> { ["RequestId"] = id }))
    {
        await next(ctx);
    }
});
```
</Stack>
<Stack id="java" lib="Spring Boot">
```java
@Component
class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader("X-Request-Id")).orElseGet(() -> UUID.randomUUID().toString());
        res.setHeader("X-Request-Id", id);
        MDC.put("requestId", id);              // every log line on this thread gets it
        try { chain.doFilter(req, res); } finally { MDC.remove("requestId"); }
    }
}
```
</Stack>
<Stack id="go" lib="net/http">
```go
func requestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-Id")
		if id == "" {
			id = uuid.NewString()
		}
		w.Header().Set("X-Request-Id", id)
		logger := slog.Default().With("requestId", id)
		next.ServeHTTP(w, r.WithContext(withLogger(r.Context(), logger)))
	})
}
```
</Stack>
<Stack id="fastapi" lib="FastAPI">
```python
@app.middleware("http")
async def request_id(request: Request, call_next):
    rid = request.headers.get("x-request-id") or str(uuid4())
    request_id_var.set(rid)                 # a ContextVar read by the log formatter
    response = await call_next(request)
    response.headers["x-request-id"] = rid
    return response
```
</Stack>
</FiveStacks>

Look at how each stack carries "the current request" to the logger. Java uses **MDC**, a thread-local map, which works because Spring MVC keeps one request on one thread. Python uses a **ContextVar**, which follows async tasks. Go passes it explicitly in `context.Context`. Node needs a child logger or `AsyncLocalStorage`. C# uses a logging scope backed by `AsyncLocal`. Same goal, five answers shaped by the concurrency models of Chapter 9.

<FromTS>
`AsyncLocalStorage` from `node:async_hooks` is Node’s equivalent of a thread-local for async code. Libraries such as `nestjs-cls` build on it so that any service can read the current request id without passing it through every function.
</FromTS>

## Timeouts at every hop

A request crosses several timers: the client’s, the load balancer’s idle timeout, the server’s read and write timeouts, and every database or HTTP call your handler makes. The rule is that **inner timeouts must be shorter than outer ones**, so your service gives up and returns an error before the load balancer cuts the connection and the client sees a blank 502.

<InTheWild>
Go’s `http.Server` has no read or write timeouts by default, and many production Go services set `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout` explicitly for that reason. Kestrel, Tomcat and Uvicorn ship with defaults, but they rarely match your load balancer. Check them on day one.
</InTheWild>

<InterviewLens>
"Walk me through what happens when a request hits your Spring service." A strong answer goes stop by stop: Tomcat accepts and parses, the filter chain runs (security, request id), `DispatcherServlet` maps the handler, interceptors run, arguments are resolved and validated, the method executes, the return value is serialised by a message converter, and exceptions are mapped by controller advice. Then it names where they would put logging, auth and validation, and why.
</InterviewLens>

Placing an order in Parcel touches three services: Ordering records it, Inventory reserves stock, Payments charges the customer. In a single database this would be one transaction. Across services there is no shared transaction, and two-phase commit across a broker and five databases is neither available nor wise. This chapter covers the two patterns that make multi-service workflows reliable anyway: the **outbox** for publishing events without losing them, and the **saga** for multi-step processes that can fail halfway.

## The dual-write problem

A handler saves the order and then publishes `OrderPlaced`. If the process crashes between the two, the order exists and nobody hears about it. Publishing first is worse: an event for an order that was never committed. Retrying does not help, because you do not know which half succeeded.

## The transactional outbox

Write the event into an **outbox** table in the **same database transaction** as the state change. Either both commit or neither does. A separate **relay** reads unpublished rows and publishes them to the broker, marking them sent.

```sql
CREATE TABLE outbox (
  id            uuid PRIMARY KEY,
  aggregate_id  text        NOT NULL,       -- becomes the Kafka key
  type          text        NOT NULL,       -- OrderPlaced
  payload       jsonb       NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
```

The relay can **poll** the table with `FOR UPDATE SKIP LOCKED` (simple, a few seconds of latency) or use **change data capture**: Debezium reads PostgreSQL’s write-ahead log and publishes outbox rows to Kafka, with no polling. Either way, delivery is at-least-once, so consumers keep an **inbox**: a table of processed event ids written in the same transaction as their own effect.

## Sagas

A **saga** replaces one distributed transaction with a sequence of local transactions. Each step commits in its own service; if a later step fails, earlier steps are undone by **compensating actions**. Parcel’s checkout:

| Step | Service | Action | Compensation |
| --- | --- | --- | --- |
| 1 | Ordering | Create order as `pending` | Mark order `cancelled` |
| 2 | Inventory | Reserve stock | Release the reservation |
| 3 | Payments | Charge the customer | Refund |
| 4 | Ordering | Mark order `confirmed` | — |

If the charge fails at step 3, Inventory releases the reservation and Ordering cancels the order. Note that compensations are business operations, not database rollbacks: a refund is visible to the customer and may itself fail and need retrying.

### Choreography or orchestration

- **Choreography**: each service reacts to the previous one’s events. Ordering publishes `OrderPlaced`; Inventory reserves and publishes `StockReserved`; Payments charges and publishes `PaymentCaptured`; Ordering confirms. No central component, easy for short flows, hard to see as a whole once there are many steps.
- **Orchestration**: an **orchestrator** (a state machine in Ordering, or a workflow engine such as Temporal) sends commands to each service and decides the next step or compensation. The flow lives in one place and is easy to change and monitor.

Parcel uses choreography for the happy path and an orchestrator in Ordering for timeouts and compensations, a common hybrid.

<Pitfall title="Forgetting the in-between states">
Between steps, the system is visibly inconsistent: an order is `pending` while stock is reserved but payment has not happened. Model these states explicitly, show them honestly in the UI ("processing payment"), add timeouts that trigger compensations, and make every step and compensation idempotent, because each message can arrive twice.
</Pitfall>

## Living with eventual consistency

Eventual consistency is not a bug to hide but a property to design for. Show pending states, read your own writes where the user expects it, set timeouts and alerts on how long a saga may stay in progress, and build a reconciliation job that finds stuck instances. Business people understand this well: banks, shops and couriers have always worked this way.

<InTheWild>
Debezium plus an outbox table is a widely used way to publish events from relational services, and workflow engines such as Temporal have made orchestrated sagas much easier to build and observe. Whatever the tooling, the review questions are the same: what happens if this step fails, if this message arrives twice, and if it never arrives.
</InTheWild>

<InterviewLens>
"How do you keep data consistent across services without distributed transactions?" A strong answer: local transactions per service, a transactional outbox to publish events reliably, idempotent consumers with an inbox, sagas with explicit compensations (choreographed or orchestrated), visible intermediate states with timeouts, and reconciliation as a safety net.
</InterviewLens>

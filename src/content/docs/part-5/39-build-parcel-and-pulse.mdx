This is where Part IV’s architecture and Part V’s distributed-systems tools meet. **Parcel** is an order pipeline split into five services, each in a different language, talking through GraphQL, REST, gRPC and Kafka. **Pulse** is a real-time chat and notification service that Parcel uses to tell customers about their orders. The code lives in the `parcel` and `pulse` repositories; this chapter is the map.

| Service | Stack | Owns | Speaks |
| --- | --- | --- | --- |
| Gateway | NestJS | Nothing (aggregates) | GraphQL to apps; REST and gRPC inward |
| Catalog | FastAPI | Products, prices | REST |
| Ordering | Spring Boot, Kotlin | Orders, the checkout saga | REST, gRPC client, Kafka |
| Inventory | Go | Stock, reservations | gRPC server, Kafka |
| Payments | ASP.NET Core | Event-sourced payments ledger | Kafka, provider webhooks |

Each service has its own PostgreSQL database (a schema per service in local Compose, separate databases in Kubernetes) and its own CI pipeline. Contracts live in a shared `contracts/` folder: `.proto` files, event schemas, OpenAPI documents, and Pact files published to a broker.

## One order, end to end

1. The app sends a `placeOrder` mutation to the **gateway**, with an idempotency key.
2. The gateway calls **Ordering**, which loads prices from **Catalog** (REST, cached) and calls **Inventory** `ReserveStock` over gRPC with an 800 ms deadline.
3. Ordering saves the order as `pending` and `OrderPlaced` to its outbox in one transaction, then answers the gateway.
4. The outbox relay publishes `OrderPlaced`. **Payments** charges the customer through the (simulated) provider and records the result in its ledger, publishing `PaymentCaptured` or `PaymentFailed`.
5. Ordering confirms the order, or compensates: it asks Inventory to release the reservation and cancels the order.
6. Ordering publishes `OrderConfirmed`; **Pulse** pushes a notification to the customer’s open app over SSE.

Every consumer uses an inbox. Here is Inventory’s, in Go:

```go
func (h *Handler) OnOrderPlaced(ctx context.Context, evt OrderPlaced) error {
	return pgx.BeginFunc(ctx, h.db, func(tx pgx.Tx) error {
		tag, err := tx.Exec(ctx, `INSERT INTO inbox (event_id) VALUES ($1) ON CONFLICT DO NOTHING`, evt.EventID)
		if err != nil {
			return err
		}
		if tag.RowsAffected() == 0 {
			return nil // already processed: a duplicate delivery
		}
		return h.reservations.ConfirmForOrder(ctx, tx, evt.OrderID)
	})
}
```

## Pulse

Pulse is a smaller service implemented in five stacks (Nest, ASP.NET with SignalR, Spring, Go, FastAPI), any of which can sit behind Parcel. It persists chat messages in PostgreSQL before broadcasting them, fans out through Redis pub/sub, serves notifications over SSE with `Last-Event-ID` resume, and authenticates connections with the same Keycloak tokens as SeatLock.

## Running it

```bash
docker compose up --build              # Kafka, Postgres, Redis, Keycloak, five services, Pulse
open http://localhost:4000/graphql     # the gateway
open http://localhost:16686            # Jaeger: traces across all services (Chapter 43)
```

## Gate: Phase 4

The roadmap’s gate: **one order traced across five services in five languages.**

- [ ] Place an order and find its trace in Jaeger: gateway, Ordering, Catalog, Inventory, the outbox relay, Payments and back.
- [ ] Stop Inventory and place an order: the gateway answers quickly with a clear error (deadline, breaker), nothing hangs.
- [ ] Make the payment provider fail: watch the saga release stock and cancel the order.
- [ ] Replay the `parcel.orders.v1` topic from the beginning for Inventory’s consumer group: no stock changes, because the inbox absorbs every duplicate.
- [ ] Connect 1,000 Pulse clients with the included k6 script, deploy a new Pulse version, and confirm every client reconnects and misses no notification.

<InTheWild>
Real polyglot systems look like this, often less tidy: a handful of languages chosen by different teams over the years, held together by contracts, a broker and shared platform tooling for deployment and observability. The skills that matter are the ones you just used: reading each language well enough to follow a request through it, and knowing which guarantees hold at each boundary.
</InTheWild>

<InterviewLens>
"Walk me through an order in your system and what happens when each step fails." A strong answer narrates the happy path with the protocol of each hop, then for every step names the failure (timeout, duplicate, crash between write and publish, payment failure) and the mechanism that handles it (deadline and breaker, inbox, outbox, compensation), and closes with how you would observe it (traces, saga dashboards, alerts on stuck orders).

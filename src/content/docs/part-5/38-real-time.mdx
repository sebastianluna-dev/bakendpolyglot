Part V’s second app, **Pulse**, is real-time chat and notifications: messages appear without refreshing, typing indicators update live, and Parcel can push "your order shipped" to the open app. Real-time changes the server’s job from answering short requests to holding long connections, and that changes how you scale. This chapter compares the transport options, shows a room broadcast in each stack, and explains how to run it on many instances.

## Four ways to get fresh data

| Technique | Direction | How | Good for |
| --- | --- | --- | --- |
| Polling | Client pulls | Request every N seconds | Rare updates, simplicity |
| Long polling | Client pulls, server holds | Request waits until data or timeout | Legacy fallback |
| Server-Sent Events | Server → client | One HTTP response that never ends | Notifications, live dashboards, LLM streaming |
| WebSockets | Both ways | Upgraded TCP connection | Chat, collaboration, games |

Choose the least powerful option that works. **SSE** is plain HTTP, passes through proxies, reconnects automatically and resumes from `Last-Event-ID`; Pulse uses it for notifications. **WebSockets** are needed when the client sends frequent messages too; Pulse uses them for chat.

```go
func (h *Hub) ServeRoom(w http.ResponseWriter, r *http.Request) {
	conn, err := websocket.Accept(w, r, nil)
	if err != nil {
		return
	}
	defer conn.CloseNow()
	room := r.PathValue("room")
	msgs := h.Subscribe(room) // local channel, fed from Redis pub/sub
	defer h.Unsubscribe(room, msgs)

	go h.readLoop(r.Context(), conn, room) // incoming messages are published to Redis
	for m := range msgs {
		if err := wsjson.Write(r.Context(), conn, m); err != nil {
			return
		}
	}
}
```

<Stack id="fastapi" lib="FastAPI + redis.asyncio">
```python
@app.websocket("/rooms/{room_id}")
async def room(ws: WebSocket, room_id: str):
    await ws.accept()
    pubsub = redis.pubsub()
    await pubsub.subscribe(f"room:{room_id}")

    async def forward() -> None:
        async for m in pubsub.listen():
            if m["type"] == "message":
                await ws.send_text(m["data"])

    task = asyncio.create_task(forward())
    try:
        while True:
            await redis.publish(f"room:{room_id}", await ws.receive_text())
    except WebSocketDisconnect:
        task.cancel()
        await pubsub.unsubscribe()
```
</Stack>
</FiveStacks>

Three stacks have a framework that manages rooms and the backplane for you (Socket.IO with its Redis adapter, SignalR with a Redis backplane, Spring with a STOMP broker relay). Go and FastAPI make the pub/sub explicit, which is more code and makes the scaling model obvious.

Long-lived connections bring their own operational rules:

- **Connection capacity** is mostly memory and file descriptors. Go, Node and .NET hold hundreds of thousands of idle sockets per instance comfortably; on the JVM, use virtual threads or a reactive stack; in Python, use ASGI.
- **Sticky sessions** are needed for Socket.IO’s and SignalR’s HTTP fallback transports; pure WebSockets stay on one instance anyway for the life of the connection.
- **Heartbeats** detect dead connections and stop proxies closing idle ones; align them with the load balancer’s idle timeout.
- **Deploys** close every connection on the old instances. Clients must reconnect with backoff and jitter and resume (SSE’s `Last-Event-ID`, a "messages since" query for chat), or a deploy becomes a self-inflicted thundering herd.
- **Authentication** happens at connection time (a token in the first message or a cookie), and long connections must handle token expiry.

<Pitfall title="Treating the socket as the source of truth">
A message that only exists in a WebSocket frame is lost if the recipient is offline or reconnecting. Persist messages first (Pulse writes to PostgreSQL), then broadcast, and let clients fetch what they missed on reconnect.
</Pitfall>

<InTheWild>
Many teams buy rather than build the connection layer (Ably, Pusher, Azure Web PubSub, AWS API Gateway WebSockets) and keep only the business logic. The design questions do not change: persistence, reconnection, fan-out and authorization per room.
</InTheWild>

<InterviewLens>
"Design the real-time layer of a chat app." A strong answer chooses WebSockets for chat and SSE for notifications, persists before broadcasting, fans out through a backplane across instances, handles reconnection with resume, heartbeats and auth on connect, and estimates connections per instance from memory per connection.
</InterviewLens>

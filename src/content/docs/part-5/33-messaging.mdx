Part V turns Parcel into five services in five languages. Services that call each other synchronously for everything fail together, so most communication in Parcel is asynchronous: a service publishes a fact ("an order was placed") and others react when they can. This chapter covers the two kinds of broker you will meet, the delivery guarantees they offer, and the producer and consumer code in each stack.

## Queues and logs

| | Queue (RabbitMQ, SQS) | Log (Kafka, Redpanda, Kinesis) |
| --- | --- | --- |
| After consumption | Message removed once acknowledged | Message kept for the retention period |
| Many independent consumers | Fan-out exchanges, one copy per queue | Each consumer group reads the same log |
| Re-reading old messages | No | Yes: reset the group’s offset |
| Ordering | Per queue, weakened by parallel consumers | Per partition, by key |
| Typical use | Work distribution, commands, jobs | Event streams, integration between services, replay |
| Routing | Rich: exchanges, bindings, topics | Simple: topic and key |

Use a **queue** when messages are tasks to be done once by whoever is free. Use a **log** when messages are facts that several services want, possibly later, possibly again. Parcel uses Kafka for domain events between services and keeps simple job queues inside services.

A topic is split into **partitions**; each is an ordered log. The producer picks a partition by hashing the message **key**, so all events with the same key (the same order) stay in order. A **consumer group** shares partitions among its members: add consumers to scale out, up to one per partition. Each group tracks its own **offset** per partition, so Inventory and Shipping read the same events independently.

## Delivery guarantees

| Guarantee | How it happens | Risk |
| --- | --- | --- |
| At-most-once | Commit the offset, then process | Crash after commit loses the message |
| At-least-once | Process, then commit | Crash before commit reprocesses it |
| Exactly-once | Transactions within the broker | Only covers broker-to-broker; your database is outside |

Choose **at-least-once** and make consumers idempotent: record processed event ids in the same transaction as the effect (an **inbox** table), or make the effect naturally idempotent ("set status to reserved"). That combination is often called **effectively-once**.

## Failures and dead letters

A message that always fails (a bug, bad data) blocks its partition forever if you retry it in place. Retry a few times with backoff, then move it to a **dead-letter topic** with the error attached, alert, and keep going. Someone fixes the cause and replays the dead letters.

<Pitfall title="Events as remote procedure calls">
An event named `ReserveStockForOrder` that Ordering publishes and then waits for is a slow, hard-to-debug RPC. Events state facts (`OrderPlaced`) and the publisher does not know or care who reacts. When you need an answer now, use a synchronous call (Chapters 35 and 37); when you need a multi-step process, use a saga (Chapter 34).
</Pitfall>

## Schemas

Events outlive the code that produced them, and consumers in other languages must parse them. Give every event a versioned schema (JSON Schema, Avro or Protobuf), keep changes additive, put the version in the topic name or a header, and validate in CI. A schema registry enforces compatibility rules at publish time.

<InTheWild>
Kafka is the default event backbone in large companies; RabbitMQ remains common for task queues; cloud teams often use SQS, SNS, EventBridge, Pub/Sub or Service Bus instead of running brokers. The concepts in this chapter (keys and ordering, consumer groups, at-least-once, dead letters, schemas) transfer directly.
</InTheWild>

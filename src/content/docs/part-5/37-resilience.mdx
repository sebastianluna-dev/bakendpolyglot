In a system of five services, something is always slightly broken: a pod restarting, a network blip, a dependency with a slow database. Resilience patterns keep those small failures small. Without them, one slow service makes its callers slow, their threads and connections fill up, and the whole system falls over, a **cascading failure**. This chapter covers the five patterns that stop the cascade and how each stack applies them.

## Five patterns

**Timeouts.** Every remote call gets a timeout, shorter than the caller’s own deadline. A call without a timeout can hold a thread or connection forever, and that is how most cascades begin.

**Retries with backoff and jitter.** Retry only transient failures (timeouts, 503, `UNAVAILABLE`) of **idempotent** operations, a small number of times, with exponentially growing, randomised delays: 100 ms, 200 ms, 400 ms, each ± 50 %. Cap retries with a **budget** (for example, at most 10 % extra traffic), or a retry storm will finish off a struggling service.

**Circuit breakers.** Track failures per dependency. After too many, **open** the circuit: fail immediately without calling, giving the dependency room to recover and giving your callers a fast error instead of a slow one. After a cool-down, go **half-open** and let a few trial calls through.

**Bulkheads.** Give each dependency its own limited pool of connections or concurrent calls. If Catalog hangs, only the Catalog pool fills up; calls to Payments still have capacity.

**Fallbacks and degradation.** Decide in advance what to show when a dependency is down: product names from a cache, recommendations hidden, "payment status pending". A degraded page beats an error page.

## The patterns, five ways

<FiveStacks note="Timeout, retry with backoff, and a circuit breaker around a Catalog call">
<Stack id="nest" lib="cockatiel">
```ts
const catalogPolicy = wrap(
  retry(handleWhen(isTransient), { maxAttempts: 3, backoff: new ExponentialBackoff() }),
  circuitBreaker(handleAll, { halfOpenAfter: 10_000, breaker: new ConsecutiveBreaker(5) }),
  timeout(800, TimeoutStrategy.Aggressive),
);

const product = await catalogPolicy.execute(({ signal }) => catalog.getProduct(sku, { signal }));
```
</Stack>
<Stack id="cs" lib="Microsoft.Extensions.Http.Resilience">
```csharp
builder.Services.AddHttpClient<CatalogClient>(c => c.BaseAddress = new Uri(catalogUrl))
    .AddStandardResilienceHandler(o =>
    {
        o.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(800);
        o.Retry.MaxRetryAttempts = 2;          // exponential backoff with jitter by default
        o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(10);
    });
```
</Stack>
<Stack id="kotlin" lib="Resilience4j">
```kotlin
@CircuitBreaker(name = "catalog", fallbackMethod = "cachedProduct")
@Retry(name = "catalog")
@TimeLimiter(name = "catalog")
suspend fun product(sku: String): Product = catalogClient.product(sku)

suspend fun cachedProduct(sku: String, e: Throwable): Product = productCache.get(sku) ?: throw e
// thresholds, wait durations and backoff live in application.yml under resilience4j.*
```
</Stack>
<Stack id="go" lib="gobreaker + context">
```go
cb := gobreaker.NewCircuitBreaker[*Product](gobreaker.Settings{
	Name:        "catalog",
	Timeout:     10 * time.Second, // open → half-open
	ReadyToTrip: func(c gobreaker.Counts) bool { return c.ConsecutiveFailures >= 5 },
})

for attempt := 0; attempt < 3; attempt++ {
	p, err := cb.Execute(func() (*Product, error) {
		ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
		defer cancel()
		return catalog.Product(ctx, sku)
	})
	if err == nil || !isTransient(err) {
		return p, err
	}
	time.Sleep(backoffWithJitter(attempt)) // 100ms, 200ms, 400ms ± 50%
}
```
</Stack>
<Stack id="fastapi" lib="tenacity + httpx">
```python
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential_jitter(initial=0.1, max=2),
    retry=retry_if_exception_type((httpx.TransportError, TransientStatus)),
)
async def get_product(sku: str) -> Product:
    resp = await client.get(f"/products/{sku}", timeout=httpx.Timeout(0.8))
    if resp.status_code in (502, 503, 504):
        raise TransientStatus(resp.status_code)
    resp.raise_for_status()
    return Product.model_validate(resp.json())
# a breaker library (pybreaker, aiobreaker) or the service mesh adds the circuit breaker
```
</Stack>
</FiveStacks>

.NET and the JVM have the most complete libraries; in Go and Python teams combine small libraries or push breakers and retries into a **service mesh** (Istio, Linkerd), which applies them uniformly to every service regardless of language. That uniformity is attractive in a polyglot system like Parcel.

<Pitfall title="Retries at every layer">
If the gateway retries 3 times, Ordering retries 3 times and its HTTP client retries 3 times, one failing call to Inventory becomes 27. Retry at one layer, usually the one closest to the failing dependency, and make the others fail fast.
</Pitfall>

## Load shedding and health checks

When a service is overloaded, serving every request slowly helps nobody. **Shed load**: reject excess requests early with `503` and `Retry-After`, using concurrency limits, so the requests you accept finish quickly. Separate **liveness** (the process is not stuck, so do not restart it) from **readiness** (it can take traffic now), and never make liveness depend on downstream services, or a database blip restarts your entire fleet (Chapter 41).

<InTheWild>
Teams learn resilience from incidents. The usual postmortem findings are a missing timeout, retries without backoff, a health check that depended on the database, and a shared connection pool. Chaos experiments, deliberately killing pods or adding latency in staging, find them before customers do.
</InTheWild>

<InterviewLens>
"Service A calls B, and B becomes slow. What happens, and how do you protect A?" A strong answer describes the cascade (threads and connections pile up in A), then applies timeouts shorter than A’s own deadline, limited retries with backoff and jitter on idempotent calls, a circuit breaker, a bulkhead for B, a fallback, and load shedding, with metrics to see each one trigger.
</InterviewLens>

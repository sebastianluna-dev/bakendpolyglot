You have written TypeScript for years, and you have shipped Express apps. This chapter is not about the language. It is about what happens underneath your handlers: one thread, an event loop, a thread pool you did not know you were using. Every other runtime in this book makes a different choice here, so this is the baseline we will compare against for the rest of the book.

## V8 runs your code; libuv runs everything else

Node is two engines glued together. **V8** compiles and runs your JavaScript on a single thread. **libuv** is a C library that talks to the operating system: sockets, files, timers, DNS. When you `await` a database query, V8 does not wait. It registers a callback, libuv watches the socket, and when bytes arrive libuv queues your callback for V8 to run.

Network I/O never touches a thread of yours: libuv asks the operating system to notify it (epoll on Linux, kqueue on macOS, IOCP on Windows). Work the OS cannot do asynchronously, such as most file system calls, `dns.lookup`, `crypto.pbkdf2` and zlib, goes to the **libuv thread pool**, which has four threads unless you set `UV_THREADPOOL_SIZE`.

Most of your request handling happens in the **poll** phase: a socket becomes readable, its callback runs, your handler runs. The rule that matters is the bar at the bottom of the figure: after each callback, Node empties the `process.nextTick` queue, then the promise microtask queue, before it runs the next callback. That is why this ordering is predictable for four of the five lines:

```ts
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');
// sync → nextTick → promise → then timeout and immediate, in either order
```

## One thread means one slow handler slows everyone

The single thread is a feature: no locks, no data races inside your process. It is also the one way to hurt every user at once.

```ts
app.get('/report', (_req, res) => {
  const result = crunchNumbers(rows); // 800 ms of pure CPU
  res.json(result);                   // every other request also waited 800 ms
});
```

<Pitfall title="Things that block the loop">
CPU-heavy loops, `JSON.parse` on a multi-megabyte body, synchronous APIs such as `fs.readFileSync` or `crypto.pbkdf2Sync` inside a handler, and regular expressions with catastrophic backtracking. None of them fail; they just make your p99 latency terrible under load.
</Pitfall>

For real CPU work, move it to a **worker thread**: a second V8 isolate with its own event loop, talking to yours by messages.

```ts
import { Worker } from 'node:worker_threads';

function crunchInWorker(rows: Row[]): Promise<Report> {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL('./crunch.worker.js', import.meta.url), { workerData: rows });
    worker.once('message', resolve);
    worker.once('error', reject);
  });
}
```

Starting a worker costs tens of milliseconds, so production code keeps a pool of them (the `piscina` library is the usual choice). And if the work is truly heavy, the honest answer is often a different service, which is exactly the kind of decision Go and Java make easier, as you will see in Chapters 5 and 7.

## Streams and backpressure

When a response is large, you should not hold it in memory. Streams move data in chunks, and **backpressure** lets a slow client tell a fast producer to pause. `stream.pipeline` wires it up and cleans up on errors:

```ts
import { pipeline } from 'node:stream/promises';
import { createReadStream } from 'node:fs';
import { createGzip } from 'node:zlib';

app.get('/export', async (_req, res) => {
  res.setHeader('Content-Type', 'text/csv');
  res.setHeader('Content-Encoding', 'gzip');
  await pipeline(createReadStream('loans.csv'), createGzip(), res);
});
```

Memory stays flat whether the file is 1 MB or 10 GB, because only a few chunks are ever in flight. Every stack in this book has the same idea under another name: `IAsyncEnumerable` in C#, `StreamingResponseBody` in Spring, `io.Copy` in Go, `StreamingResponse` in FastAPI.

## From Express to NestJS

Express gives you a router and middleware, and leaves structure to you. NestJS adds the structure enterprise teams want: modules, dependency injection, decorators, and a fixed request pipeline. The same endpoint in both:

<FiveStacks title="Two styles" note="Same endpoint, GET /books/:id" sync={false}>
<Stack id="express" lib="Express 5">
```ts
const router = express.Router();
const books = new BooksService(db);   // you wire dependencies yourself

router.get('/books/:id', async (req, res) => {
  const book = await books.find(Number(req.params.id));
  if (!book) return res.status(404).json({ error: 'Book not found' });
  res.json(book);
});
```
</Stack>
<Stack id="nest" lib="NestJS">
```ts
@Controller('books')
export class BooksController {
  constructor(private readonly books: BooksService) {}   // injected

  @Get(':id')
  async find(@Param('id', ParseIntPipe) id: number) {
    const book = await this.books.find(id);
    if (!book) throw new NotFoundException('Book not found');
    return book;
  }
}
```
</Stack>
</FiveStacks>

Three things changed. The service is **injected** instead of constructed. Parsing and validation moved into a **pipe** (`ParseIntPipe` answers 400 for `/books/abc`). And errors are **thrown**, then turned into HTTP responses by an exception filter. Express 5 got closer: a rejected promise in a handler now reaches your error middleware without a wrapper.

### Modules and dependency injection

A Nest module declares what it provides and what it exposes. The DI container builds the object graph at startup:

```ts
@Module({
  imports: [DatabaseModule],
  controllers: [BooksController],
  providers: [BooksService],
  exports: [BooksService],      // other modules may inject it
})
export class BooksModule {}
```

Providers are **singletons** by default: one `BooksService` for the whole process. Nest also supports request scope (a new instance per request) and transient scope (a new instance per consumer), but both cost allocations on every request, so use them only when a provider really holds per-request state.

<InTheWild>
This is the same idea as Spring’s IoC container and ASP.NET Core’s service collection, and Nest borrowed it on purpose. Once you know Nest’s modules, providers and scopes, Chapter 4 (ASP.NET Core’s lifetimes: singleton, scoped, transient) and Chapter 5 (Spring beans) will feel familiar. Go and Python will feel different: they mostly wire dependencies by hand.
</InTheWild>

Authorization belongs in a **guard**, because it should stop a request before any work is done:

```ts
@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest<Request>();
    return req.headers['x-api-key'] === process.env.API_KEY;
  }
}
```

Logging and timing belong in an **interceptor**, because it wraps the handler on both sides. Validation belongs in a **pipe**. Translating domain errors into HTTP status codes belongs in an **exception filter**. When every team puts each concern in the same station, a NestJS codebase becomes easy to navigate.

<Pitfall title="Unhandled rejections end the process">
Since Node 15, an unhandled promise rejection crashes the process by default. Frameworks catch errors inside handlers, but a forgotten `await` in a background task, or a `.then()` without a `.catch()`, will still take the whole server down. Run every background promise through a function that logs and handles its errors.
</Pitfall>

<InterviewLens>
"Is Node.js single-threaded?" A strong answer: your JavaScript runs on one thread per process, but Node is not single-threaded. libuv uses the operating system’s async I/O for sockets and a thread pool for file, DNS and some crypto work, and you can add worker threads for CPU work. Then say what follows: never block the loop, scale with more processes (cluster or containers), and stream large payloads.
</InterviewLens>

## The matrix

| | TypeScript | C# | Java / Kotlin | Go | Python |
| --- | --- | --- | --- | --- | --- |
| Typing | Static, structural, erased | Static, nominal, reified | Static, nominal, erased | Static, structural interfaces | Dynamic; optional hints |
| Null | `strictNullChecks` | Nullable reference types | `Optional` (Java); in the type (Kotlin) | Zero values, `nil` pointers | `None`, checked by tools |
| Errors | Exceptions | Exceptions | Checked and unchecked (Java); unchecked (Kotlin) | Returned values | Exceptions |
| Concurrency | Event loop | Thread pool + `async` | Threads, virtual threads; coroutines (Kotlin) | Goroutines + channels | Processes, threads, asyncio |
| Runs as | V8 JIT | CLR JIT | JVM JIT | Native binary | Interpreter |
| DI | Nest container | Built-in container | Spring container | By hand, in `main` | `Depends` (FastAPI); settings (Django) |
| Typical web stack | Express, NestJS | ASP.NET Core | Spring Boot | `net/http` + router | Django, FastAPI |

The practical rule: in the two left columns, *how you wait* matters (`await`, never block). In the two right columns, blocking is fine, and *what you share* matters (locks, maps, connection pools).

## The same failure, five ways

Errors are the second row that shapes your code. Here is "load a book, or answer 404" in each stack, as you will write it from Part II on:

<FiveStacks note="GET /books/:id with a 404">
<Stack id="nest" lib="NestJS">
```ts
@Get(':id')
async find(@Param('id', ParseIntPipe) id: number) {
  const book = await this.books.find(id);
  if (!book) throw new NotFoundException(`Book ${id} not found`);
  return book;
}
```
</Stack>
<Stack id="cs" lib="ASP.NET Core">
```csharp
app.MapGet("/books/{id:int}", async (int id, BooksService books, CancellationToken ct) =>
    await books.FindAsync(id, ct) is { } book
        ? Results.Ok(book)
        : Results.Problem($"Book {id} not found", statusCode: 404));
```
</Stack>
<Stack id="java" lib="Spring Boot">
```java
@GetMapping("/{id}")
Book find(@PathVariable long id) {
    return books.findById(id).orElseThrow(() -> new BookNotFound(id)); // advice → 404
}
```
</Stack>
<Stack id="go" lib="net/http">
```go
book, err := store.Find(r.Context(), id)
if errors.Is(err, ErrNotFound) {
	http.Error(w, fmt.Sprintf("book %d not found", id), http.StatusNotFound)
	return
}
```
</Stack>
<Stack id="fastapi" lib="FastAPI">
```python
book = await session.get(Book, book_id)
if book is None:
    raise HTTPException(status_code=404, detail=f"Book {book_id} not found")
return book
```
</Stack>
</FiveStacks>

Four stacks throw and translate at the edge; Go handles the error where it happens. Chapter 12 makes the response body identical in all five, using the Problem Details standard.

## Choosing a stack

There is rarely one right answer, but there are good reasons. These are the ones that hold up in real decisions:

| If you need… | Strong choices | Why |
| --- | --- | --- |
| To join an existing enterprise ecosystem | Spring Boot, ASP.NET Core | Libraries, hiring pool and conventions already there |
| Tiny, fast-starting services and infrastructure tools | Go | Static binary, low memory, simple concurrency |
| One language across frontend and backend | NestJS, Express | Shared types and people |
| A product with admin, auth and ORM on day one | Django | Batteries included, mature admin |
| An API next to data science or ML models | FastAPI | Same language as the models, async, typed |
| A modern JVM service with less ceremony | Kotlin + Spring Boot | Spring’s ecosystem, Kotlin’s ergonomics |

<InTheWild>
Most real decisions are made by the team you already have and the systems you must integrate with, not by benchmarks. A senior engineer’s job is to make that explicit: write down what the stack must do well, which risks you accept, and how you would leave if you were wrong. Chapter 48 turns that into an ADR.
</InTheWild>

## Gate: Phase 1

You finish Part I when you can pass this gate. It is deliberately small, and it must be done **from memory**, with the docs open only for library names.

- [ ] In each stack, create a new project from the command line.
- [ ] Serve `GET /books` (a hard-coded list of three books) and `GET /books/{id}`.
- [ ] Return 404 with a JSON body for an unknown id, and 400 for a non-numeric id.
- [ ] Write one automated test per stack that proves the 404.
- [ ] Note, in two lines per stack, what surprised you.

The surprises are the point. Keep the notes: they become your personal "From TypeScript" boxes for the rest of the book.

<InterviewLens>
"Why would you choose Go over Java for a new service, or the opposite?" A strong answer compares on the axes in this chapter: operational footprint and startup (Go), ecosystem and framework depth (Java), the concurrency model each team understands, existing libraries and people, and how the service will be operated. It ends with what you would measure to confirm the choice.
</InterviewLens>

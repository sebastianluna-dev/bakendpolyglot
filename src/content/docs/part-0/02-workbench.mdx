## VS Code, per language

VS Code covers four of the five stacks very well. Install these extensions; each repository also lists them in `.vscode/extensions.json`, so VS Code offers to install them when you open the folder.

| Stack | Extensions | Notes |
| --- | --- | --- |
| TypeScript | ESLint, Prettier | Built-in TypeScript support does the rest |
| C# | C# Dev Kit | Brings the solution explorer, test explorer and debugger |
| Java | Extension Pack for Java, Spring Boot Extension Pack | Maven and Gradle projects are detected automatically |
| Kotlin | Kotlin language support | Workable for reading and small edits; for heavy Kotlin work, IntelliJ IDEA is the stronger tool |
| Go | Go (by the Go team) | Installs gopls, the language server, on first use |
| Python | Python, Pylance, Ruff | Point the interpreter at the project’s `.venv` |
| All | Dev Containers, Docker | For the container setup and Compose services |

<InTheWild>
Most Java and Kotlin teams use IntelliJ IDEA, and many .NET teams use Rider or Visual Studio. You do not need them to learn, but expect to see them at work. Nothing in this book depends on an IDE: every step runs from the terminal.
</InTheWild>

## One version manager per language

Each ecosystem has a standard way to install and switch versions, and a file that pins the version for a project. Learn the pair once and you never fight versions again.

| Stack | Install and switch with | Pinned in |
| --- | --- | --- |
| Node / TypeScript | `fnm` | `.nvmrc` or `.node-version` |
| .NET | the `dotnet` SDK installer | `global.json` |
| Java and Kotlin | `SDKMAN!` | `.sdkmanrc` |
| Go | the `go` command itself | the `go` and `toolchain` lines in `go.mod` |
| Python | `uv` | `.python-version` and `pyproject.toml` |

<FromTS>
`package.json` mixes three jobs: dependencies, scripts and metadata. Other ecosystems split them. .NET puts dependencies in a `.csproj` file, Java in `build.gradle.kts` or `pom.xml`, Go in `go.mod`, and Python in `pyproject.toml`. Each also has a lockfile, and you commit it, just as you commit `package-lock.json`.
</FromTS>

## A new project in each stack

This is the command you will run at the start of every app. Each one creates a working HTTP service you can start immediately.

<FiveStacks title="New project" note="Run inside an empty folder">
<Stack id="nest" lib="Nest CLI">
```bash
npx @nestjs/cli new shelfwise
cd shelfwise && npm run start:dev
```
</Stack>
<Stack id="cs" lib=".NET CLI">
```bash
dotnet new webapi -n Shelfwise
cd Shelfwise && dotnet run
```
</Stack>
<Stack id="java" lib="Spring Initializr">
```bash
curl https://start.spring.io/starter.zip \
  -d dependencies=web -d name=shelfwise -o shelfwise.zip
unzip shelfwise.zip -d shelfwise && cd shelfwise && ./mvnw spring-boot:run
```
</Stack>
<Stack id="go" lib="go command">
```bash
mkdir shelfwise && cd shelfwise
go mod init github.com/you/shelfwise
# write main.go (the /health handler from Chapter 1), then:
go run .
```
</Stack>
<Stack id="fastapi" lib="uv">
```bash
uv init shelfwise && cd shelfwise
uv add "fastapi[standard]"
# replace the placeholder main.py with the /health app, then:
uv run fastapi dev main.py
```
</Stack>
</FiveStacks>

Go and Python are the light ones: `go mod init` creates only the module file and `uv init` a placeholder script, so you write the first handler yourself. That is deliberate, especially in Go, which prefers no scaffolding over scaffolding you must understand later.

## The Dev Container

Every companion repository ships this file. Open the folder in VS Code, accept "Reopen in Container", and every toolchain in this book is ready.

```json title=".devcontainer/devcontainer.json"
{
  "name": "backend-polyglot",
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu",
  "features": {
    "ghcr.io/devcontainers/features/node:1": {},
    "ghcr.io/devcontainers/features/dotnet:2": {},
    "ghcr.io/devcontainers/features/java:1": { "installGradle": true },
    "ghcr.io/devcontainers/features/go:1": {},
    "ghcr.io/devcontainers/features/python:1": {},
    "ghcr.io/devcontainers/features/docker-outside-of-docker:1": {}
  },
  "forwardPorts": [3000, 5432, 6379]
}
```

The databases do not live in that container. They run beside it through Docker Compose, so the same services work with local SDKs too:

```yaml title="compose.yaml"
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    ports: ["5432:5432"]
  redis:
    image: redis:7
    ports: ["6379:6379"]
```

<Pitfall>
Those credentials are for your laptop only. Never reuse a Compose file’s passwords in a deployed environment; Chapter 16 covers configuration and secrets properly.
</Pitfall>

<InterviewLens>
"How do you make sure a new engineer is productive on day one?" A strong answer covers pinned toolchains, a one-command environment (a Dev Container or a script), local dependencies in Compose, and a README that is tested by CI running the same commands.
</InterviewLens>

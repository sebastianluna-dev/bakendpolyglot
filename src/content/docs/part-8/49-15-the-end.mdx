If you have passed every gate, you have built and run the same ideas in five ecosystems, from a `GET /health` to a five-language order pipeline with traces across all of it. That breadth, combined with depth in whichever stack your next job uses, is what senior backend means.

This last chapter added a different kind of skill on top of that breadth. Building Shelfwise, SeatLock and Parcel taught you what each ecosystem is for; the problem bank trained you to write each language's basic vocabulary by hand, under a clock, with someone watching. Here is what you can do now that you could not do at the start:

- Read a backend codebase in any of the six languages and know where to look: the entry point, the request pipeline, the data access, the tests.
- Choose a stack for a service and explain the choice with its trade-offs, as in Chapter 9 and the ADRs of Chapter 48.
- Carry the same design across languages: the seat claim, the idempotency key, the outbox, the retry with backoff, each one an idea you have now written more than once.
- Write a hash map lookup, a heap, a breadth-first search and a sort with a custom order in any of the six languages from memory, and explain the cost of each line while you write it.
- Walk into a coding round in a language you use less, follow the six steps, and stay calm when a method name doesn't come to you, because the method keeps you moving.

### Keeping it

Fluency fades without use, and recall fades fastest. Small habits keep it:

- **One problem a week in a language you are not using at work.** Fifteen minutes, an easy or a medium, no assistant. It is enough to keep the vocabulary within reach.
- **Keep your recall list.** Add to it whenever you look something up, in any language, and read it before every interview.
- **Change a companion app.** Add one feature to Shelfwise or SeatLock in the stack you know least, with its tests, and run the conformance suite against it. Real code keeps the ecosystem knowledge current in a way that puzzles cannot.
- **Read other people's code in each language.** Code review (Chapter 48) is the fastest way to learn the idioms a language community actually uses.
- **Follow the releases.** Each of these languages ships a new version at least once a year. Read the release notes of the ones you use; the details in this book will slowly change, and the ideas underneath them will not.

The book ends here, but the bank doesn't have to. When you solve a problem in a way you like better, or meet a good interview problem that isn't in it, write it up in the same format, in all six languages, with its tests. Explaining a solution to someone else, in a language they know and you are still learning, is the best practice of all.

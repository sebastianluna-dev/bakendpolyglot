Almost every tree problem is one recursive function: handle the empty tree, call the function on the left and right children, and combine the two answers. These problems train that shape, and the node vocabulary that differs between the six languages: the nullable child (`TreeNode | null`, `TreeNode?`, a plain reference in Java, `*TreeNode` in Go, `TreeNode | None` in Python) and the test for a missing one. Every file builds its trees from the same level-order lists, with `null` for a missing child (`None` in Python, and a `null` constant set to `math.MinInt` in Go), so the inputs read the same in all six languages. The recursion goes as deep as the tree, so the constraints keep trees at most 500 levels deep, well below Python's default recursion limit of 1,000.

## 103 · Depth of a Tree

**Trees · Easy**

Given the root of a binary tree, return its depth: the number of nodes on the longest path from the root down to a leaf. A single node has depth 1, and the empty tree has depth 0. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [5, 2, 9, null, 4, 7, null, null, null, 6]
  output: 4            (5 → 9 → 7 → 6)

Example 2
  input:  root = [1, null, 2, null, 3]
  output: 3            (every node has only a right child)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The depth of a tree is one more than the depth of its deeper subtree, and the empty tree has depth 0; that is the whole recursion, `1 + max(depth(left), depth(right))`, and it visits every node once. There is no slower brute force worth mentioning, but there is an iterative version: a breadth-first walk with a queue counts the levels one at a time and never recurses, which matters when a tree may be deeper than the call stack allows. Write the recursive one first, because it is three lines and its shape (handle `null`, recurse on both children, combine) is the shape of every problem in this topic.

<Solutions n="103" />

**Complexity.** O(n) time, O(h) space for the call stack, where `h` is the depth (up to `n` for a tree that is a single chain).

**Common mistake.** Stopping at leaves instead of at `null`: with only a base case like "a leaf has depth 1", the call on `[1, null, 2]` still recurses into the missing left child of the root and dereferences `null`.

## 104 · Mirror a Tree

**Trees · Easy**

Given the root of a binary tree, turn it into its mirror image in place: at every node, the left and right children swap places. Return the root. The empty tree stays empty. Trees are given in level order, with null for a missing child, and the checks read the result back the same way, without trailing nulls.

```text
Example 1
  input:  root = [6, 2, 8, 1, 4, null, 9]
  output: [6, 8, 2, 9, null, 4, 1]

Example 2
  input:  root = [3, 1]
  output: [3, null, 1]   (the left child becomes a right child)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** Swapping the root's two children is not enough, because each subtree must come out mirrored too. Recursively, the new left child is the mirrored right subtree and the new right child is the mirrored left subtree, and every node is visited once. Order matters: save the old left child in a variable before overwriting it, or both sides are built from the right subtree. C#, Go and Python swap with one tuple assignment, which evaluates both mirrored subtrees before assigning either.

<Solutions n="104" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Writing `root.left = mirror(root.right)` and then `root.right = mirror(root.left)` without saving the old left child: the second line reads the value the first one just wrote, so `[3, 1]` comes back as `[3]` and the 1 is lost.

## 105 · Are Two Trees Identical?

**Trees · Easy**

Given the roots of two binary trees, `a` and `b`, return `true` if they are identical: the same shape, with equal values in the same positions. Two empty trees are identical; an empty tree and a non-empty one are not. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  a = [4, 2, 6], b = [4, 2, 6]
  output: true

Example 2
  input:  a = [4, 2], b = [4, null, 2]
  output: false        (2 is a left child in one and a right child in the other)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴` in each tree, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution writes both trees out as level-order lists, nulls included, and compares the lists: O(n + m) time and as much extra memory. Walking both trees in step needs no lists. If either node is `null`, they match only when both are; otherwise their values must be equal, the two left subtrees identical and the two right subtrees identical. Because `&&` (`and` in Python) short-circuits, the walk stops at the first difference.

<Solutions n="105" />

**Complexity.** O(min(n, m)) time, since the walk never goes past the smaller tree; O(h) space for the call stack.

**Common mistake.** Comparing traversals of the values alone, without the missing children: in preorder, `[4, 2]` and `[4, null, 2]` both read 4, 2, although their shapes differ.

## 106 · Is the Tree Symmetric?

**Trees · Easy**

Given the root of a binary tree, return `true` if it is symmetric: its own mirror image, so that the left subtree is the mirror of the right subtree in shape and in values. The empty tree and a single node are symmetric. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [7, 4, 4, 1, 9, 9, 1]
  output: true

Example 2
  input:  root = [5, 3, 3, 8, null, null, 2]
  output: false        (the shape is mirrored, but 8 faces 2)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution copies the tree, mirrors the copy as in problem 104, and compares it with the original as in problem 105: O(n) time, but O(n) extra memory for the copy. A helper `isMirror(a, b)` does both at once without the copy. It walks two subtrees in step like problem 105, but pairs the outer children (`a.left` with `b.right`) and the inner ones (`a.right` with `b.left`). The tree is symmetric when it is empty or when its root's two subtrees are mirrors of each other.

<Solutions n="106" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Pairing `a.left` with `b.left` as in problem 105, which tests whether the two halves are copies rather than mirrors and returns `false` for Example 1, whose left half `4 → 1, 9` mirrors the right half `4 → 9, 1`.

## 107 · Is the Tree Height-Balanced?

**Trees · Easy**

A binary tree is height-balanced when, at every node, the depths of the left and right subtrees differ by at most one, with depth counted as in problem 103 (an empty subtree has depth 0). Given the root of a binary tree, return `true` if it is height-balanced. The empty tree is balanced. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [10, 5, 15, null, null, 12, 20]
  output: true

Example 2
  input:  root = [10, 5, null, 3, null, 1]
  output: false        (at the root, the left subtree has depth 3 and the right one 0)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution checks the rule at every node by calling problem 103's depth function on both children. It is correct, but every ancestor recomputes the depth of the same subtrees, which is O(n²) on a tree shaped like a chain. Computing the heights bottom-up, once, removes that repeated work: a helper returns the height of its subtree, or `-1` as soon as any subtree inside it is unbalanced. Each node checks both children's results for `-1`, then the difference between them, and either passes `-1` up or returns one more than the larger height, so a single post-order pass decides the whole tree.

<Solutions n="107" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Checking the rule only at the root: `[1, 2, 3, 4, null, null, 5, 6, null, null, 7]` has subtrees of depth 3 and 3 under the root, but node 2 has a left subtree of depth 2 and no right one, so the tree is not balanced.

## 108 · Longest Path Between Two Nodes

**Trees · Easy**

Given the root of a binary tree, return the length, in edges, of the longest path between any two of its nodes. A path follows parent–child links and never visits a node twice, and it does not have to pass through the root. The empty tree and a single node have a longest path of 0. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [8, 4, 11, 2, 6, null, null, 1]
  output: 4            (1 → 2 → 4 → 8 → 11)

Example 2
  input:  root = [1, 2, null, 3, 4, 5, null, null, 6, 7, null, null, 8]
  output: 6            (7 → 5 → 3 → 2 → 4 → 6 → 8, which never reaches the root)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** Every path has one highest node, where it stops going up and starts going down, and the longest path turning at a node goes down the deepest branch on each side. With depth counted in nodes as in problem 103, that path has `depth(left) + depth(right)` edges. The simple solution computes this at every node with separate depth calls, which is O(n²) on a chain. But the depth function already has both numbers in hand at each node, so it can record the best `left + right` as a side effect while it returns `1 + max(left, right)` to its parent, and one pass is enough. The best value lives in a variable that a nested function updates; Java has no nested function that can change a local variable, so it passes a one-element array to a static helper.

<Solutions n="108" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Computing `depth(left) + depth(right)` at the root only, which returns 4 instead of 6 for Example 2, because the longest path there turns at node 2.

## 109 · A Root-to-Leaf Path With a Given Sum

**Trees · Easy**

Given the root of a binary tree and a target, return `true` if some path from the root down to a leaf has values that add up to the target. A leaf is a node with no children, and a path must end at one. Values and the target may be negative. The empty tree has no paths, so it returns `false` for every target, including 0. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [5, 3, 8, 1, null, null, 4], target = 9
  output: true         (5 + 3 + 1)

Example 2
  input:  root = [2, 7], target = 2
  output: false        (2 has a child, so it is not a leaf; the only path is 2 + 7)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-1000 ≤ val ≤ 1000`, `-10⁶ ≤ target ≤ 10⁶`.

**Approach.** The simple solution collects the sum of every root-to-leaf path in a list and then looks for the target, which costs a list as long as the number of leaves. Carrying what is still missing needs no list: each node subtracts its value from the target and asks its children whether either can make up the rest, and a leaf answers whether its value is exactly what remains. The `||` (`or` in Python) stops at the first path that works. Because values can be negative, a branch cannot be abandoned early when its running sum passes the target.

<Solutions n="109" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Treating `null` as the end of a path, with a base case like "an empty tree matches when the target is 0": the missing right child of the root in Example 2 then "ends" a path with sum 2, and the answer comes out `true`.

## 110 · Sum of a Key Range in a BST

**Trees · Easy**

Given the root of a binary search tree and two keys `lo ≤ hi`, return the sum of every key `k` with `lo ≤ k ≤ hi`; both ends are included. In a binary search tree the keys are distinct, every key in a node's left subtree is smaller than the node's key, and every key in its right subtree is larger. If no key falls in the range, return 0. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [20, 10, 30, 5, 15, 25, 40], lo = 12, hi = 27
  output: 60           (15 + 20 + 25)

Example 2
  input:  root = [8, 3, 12, null, 6], lo = 9, hi = 11
  output: 0
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `1 ≤ key ≤ 10⁵`, `1 ≤ lo ≤ hi ≤ 10⁵`, so the sum fits in a 32-bit `int`.

**Approach.** The simple solution visits every node and adds the keys in the range: O(n), and it ignores the ordering. The ordering lets the walk skip whole subtrees. If a node's key is below `lo`, everything in its left subtree is smaller still, so only the right subtree can contribute; if it is above `hi`, only the left subtree can. Otherwise the key counts, and both subtrees may hold more. Out-of-range nodes are visited only along the paths towards `lo` and `hi`, so the walk touches the keys in the range plus O(h) others.

<Solutions n="110" />

**Complexity.** O(h + r) time, where `r` is the number of keys in the range (O(n) in the worst case); O(h) space for the call stack.

**Common mistake.** Skipping a node with `key <= lo` instead of `key < lo`, which drops `lo` itself: for Example 1's tree with `lo = 10` and `hi = 20` it returns 35 instead of 45.

## 111 · Level-by-Level Traversal

**Trees · Medium**

Given the root of a binary tree, return its values level by level: one list per level, from the root down, and each list from left to right. The empty tree returns an empty list. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [8, 4, 12, 2, null, 10, 14]
  output: [[8], [4, 12], [2, 10, 14]]

Example 2
  input:  root = [5, 6, null, 7, 8]
  output: [[5], [6], [7, 8]]   (7 and 8 are both children of 6)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** A simple solution computes the depth first and then, for each level `d`, walks the whole tree to collect the nodes at depth `d`: O(n·h), because the top of the tree is walked again for every level. A breadth-first walk visits each node once. Keep the current level as a list of nodes, starting with the root; its values become one row of the answer, and its children, taken left to right, become the next level. Stop when a level is empty. This is the same walk as a queue-based BFS, with the level boundary made explicit by swapping lists instead of counting queue entries.

<Solutions n="111" />

**Complexity.** O(n) time, O(n) space for the answer, plus O(w) for the two level lists, where `w` is the widest level.

**Common mistake.** With a single queue, using its live length as the loop bound while children are being added to it: the level never ends, and Example 1 comes back as one row, `[[8, 4, 12, 2, 10, 14]]`.

## 112 · What You See From the Right

**Trees · Medium**

Imagine standing to the right of a binary tree and looking at it: on each level you see only the rightmost node. Given the root, return the values you see, from the root level down. A node hidden on one level can show through on a deeper level if nothing stands to its right there. The empty tree returns an empty list. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [10, 4, 15, 2, 6, null, 20, null, null, 5]
  output: [10, 15, 20, 5]   (5 sits under 4's subtree, but nothing is to its right)

Example 2
  input:  root = [1, 2]
  output: [1, 2]            (a left child is visible when it is alone on its level)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution is problem 111's traversal, keeping the last value of each level: already O(n), but it holds a whole level in memory. A depth-first walk does it with only the call stack. Visit the right child before the left one, and carry the depth: the first node reached at each depth is the rightmost one on that level. Since the answer list has one entry per depth already seen, a node is new on its level exactly when `depth` equals the length of the list.

<Solutions n="112" />

**Complexity.** O(n) time, O(h) space for the call stack (plus the answer).

**Common mistake.** Following right children only, from the root down: that misses nodes that show through from a left subtree, so Example 1 returns `[10, 15, 20]` and Example 2 returns `[1]`.

## 113 · Validate a Binary Search Tree

**Trees · Medium**

Given the root of a binary tree, return `true` if it is a binary search tree: for every node, every key in its left subtree is strictly smaller than the node's key, and every key in its right subtree is strictly larger. Equal keys anywhere make it invalid. The empty tree is valid. Keys can be any 32-bit integer, including the smallest and largest. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [8, 4, 12, 2, 6, 10, 14]
  output: true

Example 2
  input:  root = [8, 4, 12, 2, 9, 10, 14]
  output: false        (9 is larger than its parent 4, but it sits left of 8)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-2³¹ ≤ key ≤ 2³¹ - 1`.

**Approach.** Checking each node against its two children is not enough, because the rule is about whole subtrees. A correct simple solution walks the tree in order and checks that the keys come out strictly increasing, which costs a list of all `n` keys. Passing bounds down avoids the list: each node must lie strictly between a lower and an upper bound, its left child inherits the upper bound from it and its right child the lower bound. Here the bounds are the ancestor nodes themselves, or null for "no bound yet", rather than numbers: a numeric sentinel such as `Integer.MIN_VALUE` collides with a real key of -2³¹, while a node reference cannot. 64-bit bounds or ±infinity also work.

<Solutions n="113" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Starting the bounds at the 32-bit minimum and maximum and comparing strictly: the valid tree `[-2147483648, null, 2147483647]` is then rejected, because the root is not strictly greater than the starting lower bound.

## 114 · The k-th Smallest Key in a BST

**Trees · Medium**

Given the root of a binary search tree and an integer `k`, return the `k`-th smallest key, counting from 1. In a binary search tree the keys are distinct, every key in a node's left subtree is smaller than the node's key, and every key in its right subtree is larger. `k` is always between 1 and the number of nodes. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [20, 10, 30, 5, 15, 25, 40], k = 3
  output: 15           (5, 10, 15, ...)

Example 2
  input:  root = [6, 3, 8, 1, 4, null, 9, null, 2], k = 2
  output: 2            (2 is the right child of 1)
```

Constraints: `1 ≤ k ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁹ ≤ key ≤ 10⁹`.

**Approach.** The simple solution collects every key with an in-order walk, which produces them sorted, and returns the one at index `k - 1`: O(n) time and space even when `k` is 1. The walk can stop as soon as it has produced `k` keys. Write it iteratively with an explicit stack: push the path down the left edge, pop a node (the smallest key not yet counted), count it, then continue from its right child. When the count reaches `k`, the popped key is the answer, and nothing to its right has been touched.

<Solutions n="114" />

**Complexity.** O(h + k) time, O(h) space for the stack.

**Common mistake.** Counting with a recursive in-order walk that receives `k` as a plain parameter: the decrements made inside the left subtree are lost when the call returns, so Example 1 returns 40 instead of 15.

## 115 · Lowest Common Manager

**Trees · Medium**

A company's org chart is a binary tree: each person is a node with a distinct id, and has at most two direct reports. A person's team is that person plus everyone below them. Given two ids `a` and `b`, both in the chart, return the id of their lowest common manager: the person furthest from the root whose team includes both. If `a` is above `b`, the answer is `a`; if `a` and `b` are equal, it is that id. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [1, 2, 3, 4, 5, 6, 7, null, null, 8, 9], a = 8, b = 4
  output: 2            (8 is under 5, which reports to 2, like 4)

Example 2
  input:  root = [1, 2, 3, 4, 5, 6, 7, null, null, 8, 9], a = 5, b = 9
  output: 5            (9 is in 5's team, and 5 is in its own)
```

Constraints: `1 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, ids are distinct with `1 ≤ id ≤ 10⁵`, and `a` and `b` are both in the tree.

**Approach.** The simple solution records the path from the root to `a` and the path to `b`, then walks both from the start and returns the last id they share: O(n) time, plus two path lists. One recursive walk needs no lists. It returns a node when that node is `a` or `b`, without looking further down, since the other id is either below it (and the node is the answer) or elsewhere. Otherwise it asks both children; if both report a find, `a` and `b` are on different sides and the current node is the lowest common manager, and if only one side reports, that report is passed up. The guarantee that both ids are present is what makes the early return safe.

<Solutions n="115" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Reusing the binary search tree shortcut (go left when both ids are smaller than the node, right when both are larger): an org chart is not ordered, so for Example 1 it walks 1 → 3 → 7 and returns 7 instead of 2.

## 116 · Rebuild a Tree From Two Traversals

**Trees · Medium**

Given the preorder (node, left subtree, right subtree) and inorder (left subtree, node, right subtree) traversals of the same binary tree, whose values are distinct, rebuild the tree and return its root. Two empty arrays give the empty tree. The checks read the result back in level order, with null for a missing child and without trailing nulls.

```text
Example 1
  input:  preorder = [8, 4, 2, 6, 12, 14], inorder = [2, 4, 6, 8, 12, 14]
  output: [8, 4, 12, 2, 6, null, 14]

Example 2
  input:  preorder = [1, 2, 3], inorder = [3, 2, 1]
  output: [1, 2, null, 3]   (every node has only a left child)
```

Constraints: `0 ≤ preorder.length = inorder.length ≤ 10⁴`, values are distinct with `-10⁴ ≤ val ≤ 10⁴`, both arrays come from the same tree, and the depth is at most 500.

**Approach.** The first preorder value is the root; finding it in the inorder array splits that array into the left subtree (everything before it) and the right subtree (everything after), and the size of the left part says where the right subtree starts in the preorder. Recursing with a linear search for each root, or with sliced copies of the arrays, costs O(n²) on a tree that is a single chain. Two changes make it O(n): a hash map from value to inorder position, built once, and index ranges instead of copies. Each call gets `pre`, where its subtree starts in the preorder, and `lo..hi`, its range in the inorder; the right subtree starts at `pre + 1 + (mid - lo)`, after the root and the `mid - lo` nodes of the left subtree.

<Solutions n="116" />

**Complexity.** O(n) time, O(n) space for the map, plus O(h) for the call stack.

**Common mistake.** Starting the right subtree at `pre + 1 + mid` instead of `pre + 1 + (mid - lo)`: `mid` is a position in the whole inorder array, so the formula is right only while `lo` is 0, and in Example 1 the call for 12's right subtree reads index 9 of a 6-element `preorder`.

## 117 · Nodes No Smaller Than Their Ancestors

**Trees · Medium**

Call a node good if its value is at least as large as every value on the path from the root down to it, the node itself excluded. The root is always good. Given the root of a binary tree, return the number of good nodes; the empty tree has none. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [5, 3, 8, 6, 2, 5, 9]
  output: 4            (5, 8, 6 and 9; the 5 under 8 is not good)

Example 2
  input:  root = [2, 2, 2]
  output: 3            (equal to an ancestor still counts)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution walks back up from every node and compares it with each ancestor, which needs parent links or a stored path and costs O(n·h). All a node needs to know about its ancestors is their largest value, and that is cheap to carry down. Walk from the root with a `highest` parameter, starting at the root's own value: a node is good when its value is at least `highest`, and its children receive the larger of the two. Sum the counts from both subtrees.

<Solutions n="117" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Comparing a node only with its parent: in `[5, 3, null, 4]` the 4 is larger than its parent 3 but smaller than the root, so the answer is 1, not 2.

## 118 · Flatten a Tree Into a List

**Trees · Medium**

Given the root of a binary tree, flatten it in place into a chain that follows preorder (node, left subtree, right subtree): every left child becomes null, and each node's right child becomes the next node in preorder. Reuse the existing nodes and return nothing. The empty tree stays empty. Trees are given in level order, with null for a missing child, and the checks read the flattened tree back the same way, without trailing nulls.

```text
Example 1
  input:  root = [10, 5, 20, 3, 7, null, 25]
  output: [10, null, 5, null, 3, null, 7, null, 20, null, 25]

Example 2
  input:  root = [1, 2, null, 3]
  output: [1, null, 2, null, 3]   (a left chain turns into a right chain)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁴ ≤ val ≤ 10⁴`.

**Approach.** The simple solution records the nodes in preorder in a list and then relinks them, which needs O(n) extra space. The relinking can happen as you go, with no list and no recursion. At each node that has a left subtree, find the tail of that subtree (the last node in its preorder, reached by following right children from the left child), hang the node's current right subtree off the tail, move the left subtree to the right, and set the left child to null. Then step to the right child and repeat. The order of the three pointer moves matters: the old right subtree must be attached to the tail before `right` is overwritten.

<Solutions n="118" />

**Complexity.** O(n) time, since every node is on at most one tail search; O(1) extra space.

**Common mistake.** Assigning `node.right = node.left` before the old right subtree is attached to the tail: nothing points to it any more, so Example 1 comes back without 20 and 25.

## 119 · Count Downward Paths With a Given Sum

**Trees · Medium**

Given the root of a binary tree and a target, count the downward paths whose values add up to the target. A downward path starts at any node and goes down through children to any node at or below it; a single node is a path. Values and the target may be negative, and two paths count separately when they use different nodes, even if their values match. The empty tree has no paths. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [4, 2, -1, 1, 3, null, 5], target = 5
  output: 2            (2 → 3, and 5 alone)

Example 2
  input:  root = [1, -1, 1, 1], target = 1
  output: 4            (each of the three 1s alone, and 1 → -1 → 1)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-10⁹ ≤ val ≤ 10⁹`, `-2 × 10⁹ ≤ target ≤ 2 × 10⁹`.

**Approach.** The simple solution starts a walk at every node and adds values on the way down, counting each time the running sum hits the target: O(n·h). This is problem 018's prefix-sum idea moved onto a tree. Walking from the root, keep the sum of the values from the root to the current node; a downward path ending here sums to the target exactly when some ancestor's root sum equals `current - target`. A hash map counts the root sums along the current path (seeded with 0 once, for paths that start at the root), so each node adds `map[current - target]` in O(1). Remove the node's sum from the map before returning to its parent, because that sum belongs to this branch only. A path of 500 values near 10⁹ sums to about 5 × 10¹¹, so the sums are 64-bit (`long`, `Long`, `int64`).

<Solutions n="119" />

**Complexity.** O(n) time, O(h) space for the map and the call stack.

**Common mistake.** Forgetting to remove a node's sum from the map on the way back up: sums from the left branch are then counted as ancestors of the right one, and Example 2 returns 5 instead of 4.

## 120 · Serialize and Deserialize a Tree

**Trees · Hard**

Write two functions. `serialize(root)` turns a binary tree into a string in this exact format: the nodes in preorder (node, left subtree, right subtree), each node written as its value in decimal (with a leading `-` when negative), each missing child written as `#`, and the tokens separated by single commas, with no spaces and no trailing comma. The empty tree is `"#"`. `deserialize(data)` takes a string in that format and returns the tree it describes, so `deserialize(serialize(root))` rebuilds the same shape and values. Trees are given in level order, with null for a missing child, and the checks read rebuilt trees back the same way.

```text
Example 1
  input:  serialize, root = [7, 3, 9, null, 4, 8]
  output: "7,3,#,4,#,#,9,8,#,#,#"

Example 2
  input:  deserialize, data = "5,-2,#,#,#"
  output: [5, -2]      (5, its left child -2 with two missing children, then 5's missing right child)
```

Constraints: `0 ≤ number of nodes ≤ 10⁴`, the depth is at most 500, `-1000 ≤ val ≤ 1000`, and `deserialize` only receives strings that `serialize` could produce.

**Approach.** Preorder alone cannot be decoded, because it does not say where a subtree ends; writing an explicit marker for every missing child fixes that. With the markers, a tree of `n` nodes is exactly `2n + 1` tokens, and reading them back is the same recursion as writing them: read a token, return null if it is `#`, otherwise make a node and read its left subtree and then its right one. A shared cursor over the tokens is all the state that recursion needs, since each call consumes exactly the tokens of its own subtree. Level order with markers also works, but it needs a queue on both sides; the preorder version is shorter to write under pressure. Java, Kotlin and Python read the tokens through an iterator, while TypeScript, C# and Go keep an index.

<Solutions n="120" />

**Complexity.** O(n) time for each function, O(n) space for the tokens and the string, plus O(h) for the call stack.

**Common mistake.** Leaving out the null markers: `[1, 2]` and `[1, null, 2]` both serialize to `"1,2"`, and no deserializer can tell which one it was given.

## 121 · Maximum Path Sum

**Trees · Hard**

A path in a binary tree is a sequence of nodes where each consecutive pair is joined by an edge and no node appears twice; it can start and end anywhere, and it may go up through a node and down again on the other side. It has at least one node. Given the root of a non-empty tree whose values may be negative, return the largest sum of the values on any path. Trees are given in level order, with null for a missing child.

```text
Example 1
  input:  root = [6, -8, 3, null, 9, -1, 4]
  output: 14           (9 → -8 → 6 → 3 → 4; crossing the -8 pays off)

Example 2
  input:  root = [-3, -1, -2]
  output: -1           (every value is negative, so the best path is one node)
```

Constraints: `1 ≤ number of nodes ≤ 3 × 10⁴`, the depth is at most 500, `-1000 ≤ val ≤ 1000`.

**Approach.** Every path has one highest node, where it turns: the simple solution tries each node as that top and computes the best downward path from each of its children separately, which repeats the same subtree work and costs O(n·h). One post-order walk computes it once. For each node, `gain(node)` returns the best sum of a path that starts at the node and goes down one side; a child's gain below zero is replaced by 0, because the path can simply leave that branch out. With the two children's gains, the best path that turns at this node is `val + left + right`, which updates the running answer, while the parent can only extend a path through one side, so the function returns `val + max(left, right)`. Start the answer at the root's value, not 0, so an all-negative tree is answered correctly. Java has no local functions, so its running best lives in a one-element array that the helper updates.

<Solutions n="121" />

**Complexity.** O(n) time, O(h) space for the call stack.

**Common mistake.** Starting the best sum at 0: a tree whose values are all negative, like Example 2, then returns 0, the sum of an empty path, instead of -1.

## 122 · A Word Dictionary With Wildcards

**Trees · Hard**

Design `WordDictionary`, a set of words with two operations: `addWord(word)` stores a word, and `search(pattern)` returns `true` if some stored word matches the pattern. A pattern matches a word of the same length when every letter is equal, and a `.` in the pattern matches any one letter. Only whole words match: a stored word that merely starts with the pattern does not. Adding a word twice is the same as adding it once, and a new dictionary is empty.

```text
Example 1
  calls:   addWord("loan"), addWord("lean"), search("l.an"), search("lo"), search("l...")
  returns: true, false, true   (from the three searches; "lo" is only a prefix)

Example 2
  calls:   search("."), addWord("a"), search("."), search("b")
  returns: false, true, false
```

Constraints: words have `1` to `25` lowercase letters `a`–`z`; patterns have `1` to `25` characters, each a lowercase letter or `.`, with at most 3 dots; at most `10⁴` calls in total.

**Approach.** The simple solution keeps a list of words and compares the pattern with each one: O(n·L) per search for `n` words of length up to `L`. A trie shares the work between words with a common beginning. Each node has 26 child slots and an `isWord` flag; `addWord` walks down from the root, creating the missing nodes, and marks the last one. `search` walks the same way, one pattern character per level: a letter follows one child, and a `.` tries every child that exists, returning as soon as one branch matches. At the end of the pattern the answer is the node's flag, not merely the fact that the node exists, which is what keeps prefixes from matching.

<Solutions n="122" />

**Complexity.** `addWord` is O(L). `search` is O(L) for a pattern without dots and at most O(26ᵈ × L) with `d` dots, since every dot can branch to all 26 letters. O(total letters added × 26) space for the trie.

**Common mistake.** Returning `true` when the walk reaches the end of the pattern instead of returning that node's `isWord` flag: after `addWord("loan")`, `search("lo")` then answers `true`.

A team’s speed is mostly decided by its pipeline. If merging is scary, deploys are weekly and rollbacks take an hour, every other improvement is capped. This chapter lays out the pipeline every companion app uses, the matrix that tests eight implementations at once, and the release strategies that make deploying boring.

Fast feedback first: linting and unit tests fail in a minute or two; integration and contract tests follow; the image is built once, scanned, given an SBOM and signed; then the **same digest** moves through staging and production.

## A matrix for eight implementations

Shelfwise’s CI runs the same jobs for every stack with a matrix, so adding a stack means adding a line:

```yaml title=".github/workflows/ci.yml (excerpt)"
jobs:
  stack:
    strategy:
      fail-fast: false
      matrix:
        stack: [express, nest, aspnet, spring-java, spring-kotlin, go, django, fastapi]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Unit and integration tests
        run: make -C apps/shelfwise/stacks/${{ matrix.stack }} test   # each stack's Makefile knows its toolchain
      - name: Build image
        run: docker build -t shelfwise-${{ matrix.stack }} apps/shelfwise/stacks/${{ matrix.stack }}
      - name: Conformance suite
        run: |
          cd apps/shelfwise
          docker compose --profile ${{ matrix.stack }} up -d --wait
          npm --prefix conformance ci && SHELFWISE_URL=http://localhost:3000 npm --prefix conformance test
```

Each stack’s `Makefile` hides its toolchain behind the same targets (`test`, `build`, `lint`), a small convention that lets one pipeline drive five ecosystems. Cache dependencies per stack (`actions/setup-*` caches, Gradle and NuGet caches, Go module cache, uv cache) or the matrix becomes slow.

## Release strategies

| Strategy | How | Rollback | Cost |
| --- | --- | --- | --- |
| Rolling | Replace pods gradually | Roll forward or redeploy previous | Low |
| Blue-green | Two full environments, switch the router | Instant: switch back | Double capacity during release |
| Canary | Small share of traffic to the new version, increased while metrics stay healthy | Shift traffic back | Needs traffic splitting and good metrics |
| Feature flags | Deploy dark, enable per user or percentage | Turn the flag off | Flag management and cleanup |

**Deploy** (code reaches production) and **release** (users see the change) do not have to be the same moment. Feature flags separate them, which makes deploys small and frequent and releases a business decision.

<Pitfall title="Migrations that break the running version">
The pipeline runs migrations before the new pods start, while old pods still serve traffic. A migration that renames or drops a column breaks them. Use expand and contract: add the new column, deploy code that writes both, backfill, switch reads, and only then remove the old column in a later release.
</Pitfall>

## Supply chain

Your pipeline is also an attack surface. Pin third-party actions to commit SHAs, give CI credentials the least privilege and short lifetimes (OIDC federation to your cloud instead of stored keys), require reviews on the pipeline files, and verify image signatures at deploy time so only images your pipeline built can run.

<InTheWild>
The DORA research measures delivery performance with four metrics: deployment frequency, lead time for changes, change failure rate and time to restore service. High performers deploy small changes many times a day and restore quickly. The practices in this chapter (trunk-based development, fast tests, one artefact, progressive delivery) are the ones that research associates with those results.
</InTheWild>

A strong answer: trunk-based development with small PRs, fast lint and unit stages, integration and contract tests, one image built, scanned, signed and promoted by digest, backward-compatible migrations as a separate step, canary or blue-green with automated rollback on SLO breaches, feature flags to decouple release, and DORA metrics to track it.

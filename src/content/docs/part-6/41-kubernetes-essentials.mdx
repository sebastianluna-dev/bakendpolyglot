Kubernetes is a large system, but the part a backend engineer works with every week is small: describe how your service runs, how it is reached, how healthy looks, and how much it may use. This chapter covers those objects with Parcel’s Ordering service as the example, and the behaviours that cause most production surprises.

| Object | Purpose |
| --- | --- |
| Pod | One or more containers scheduled together; the unit that runs |
| Deployment | Desired pods (image, replicas, probes, resources) and rolling updates |
| Service | Stable DNS name and load balancing to ready pods |
| Ingress / Gateway | HTTP routing from outside the cluster, TLS |
| ConfigMap / Secret | Configuration and secrets, exposed as env vars or files |
| HorizontalPodAutoscaler | Changes replica count with load |
| PodDisruptionBudget | Keeps a minimum number of pods up during node maintenance |
| Job / CronJob | Run-to-completion and scheduled work (migrations, the hold reaper) |

## A Deployment, annotated

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ordering
spec:
  replicas: 3
  selector: { matchLabels: { app: ordering } }
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 1 }     # never drop below 3 during a deploy
  template:
    metadata: { labels: { app: ordering } }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: ordering
          image: ghcr.io/parcel/ordering:1.14.2           # immutable tag, never :latest
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: ordering-config }
            - secretRef: { name: ordering-secrets }
          resources:
            requests: { cpu: 250m, memory: 512Mi }
            limits:   { memory: 768Mi }                   # no CPU limit: avoid throttling
          startupProbe:
            httpGet: { path: /health/live, port: 8080 }
            failureThreshold: 30
            periodSeconds: 2                              # up to 60 s for a slow JVM start
          readinessProbe:
            httpGet: { path: /health/ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }
            periodSeconds: 10
          lifecycle:
            preStop: { sleep: { seconds: 5 } }            # let the Service stop routing first
```

## Probes, done right

Three probes, three questions:

- **Startup**: has the app finished starting? Until it passes, the other probes are not run. Essential for JVM and .NET apps that warm up slowly.
- **Readiness**: can it take traffic **now**? It may check that the database pool is usable. Failing it removes the pod from the Service without restarting it.
- **Liveness**: is the process stuck beyond recovery? It should check only the process itself. Failing it restarts the container.

Every stack has health-check support that separates the two endpoints: ASP.NET Core health checks with tags, Spring Boot Actuator’s liveness and readiness groups, `@nestjs/terminus`, a pair of handlers in Go, and a small router in FastAPI or Django.

<Pitfall title="Liveness that checks the database">
If liveness fails when the database is slow, Kubernetes restarts every pod at once, which turns a database hiccup into a full outage and a thundering herd of reconnections when they come back. Dependencies belong in readiness, at most.
</Pitfall>

## Resources

**Requests** are what the scheduler reserves; **limits** are the ceiling. Exceed the memory limit and the container is OOM-killed; exceed a CPU limit and it is throttled, which shows up as mysterious latency. A common, defensible policy: set memory request and limit from measured usage plus headroom, set a CPU request, and leave CPU unlimited unless the cluster requires it. Tell the runtime what it has (Chapter 40): the JVM, .NET, Node and Go all read the limits, but heap and GC settings should match them.

## Rollouts and the readiness gap

During a rolling update, a new pod becomes ready and an old pod receives `SIGTERM`. For a few seconds, some traffic may still be routed to the old pod while it shuts down. The `preStop` sleep keeps it serving while endpoints update, and graceful shutdown (Chapter 40) drains what remains. Database migrations run as a separate Job before the rollout, and must be backward compatible with the old version still running (Chapter 15).

<InTheWild>
Most backend engineers do not write raw manifests for long: Helm charts, Kustomize overlays or an internal platform generate them from a few values. The concepts above are what you configure through those tools, and what you read when a pod is crash-looping at 3 a.m. (`kubectl describe pod`, `kubectl logs --previous`, events).
</InTheWild>

<InterviewLens>
"Your pods restart in a loop after a deploy. How do you investigate?" A strong answer: check events and the previous container’s logs, look for OOM kills against memory limits, startup taking longer than the probes allow, liveness depending on a failing dependency, missing configuration or secrets, and a migration the new version expected; then fix the cause and roll back if needed.
</InterviewLens>

When the Phase 4 gate asked you to find one order in Jaeger, you used the result of this chapter. Monitoring tells you that something is wrong; **observability** lets you ask why, including questions nobody anticipated, by looking at what the system emits. In a polyglot system, that only works if all five stacks emit the same signals in the same format. This chapter sets that standard: structured logs, RED metrics and distributed traces, all through **OpenTelemetry**.

## Three signals

| Signal | What it is | Cost | Best for |
| --- | --- | --- | --- |
| Logs | Timestamped events with detail | High at volume | What exactly happened to this request |
| Metrics | Aggregated numbers over time | Low | Is it healthy, is it getting worse, alerting |
| Traces | A tree of timed spans for one request across services | Medium (sampled) | Where the time went, which hop failed |

The power is in connecting them: a latency spike on a metric dashboard links to example traces, a slow span links to the logs written during it, because every log line carries the **trace id**.

## Structured logs

Log JSON, not prose, with consistent field names across stacks: `timestamp`, `level`, `message`, `service`, `trace_id`, `span_id`, plus domain fields such as `order_id`. Each stack has a standard structured logger (pino, `Microsoft.Extensions.Logging` with a JSON formatter, Logback with a JSON encoder, `log/slog`, `structlog`), and OpenTelemetry’s instrumentation can inject trace ids into them.

Log at boundaries and decisions (request received and answered, external call failed, saga step compensated), not on every line of code, and never log secrets or full personal data (Chapter 16).

## Metrics

For every service, start with **RED**: request **R**ate, **E**rror rate, **D**uration as a histogram (so you can read p50, p95, p99). For resources such as pools, queues and brokers, use **USE**: **U**tilisation, **S**aturation, **E**rrors. Add a few business metrics that matter: orders placed per minute, saga compensations, consumer lag on each Kafka topic.

Report latency percentiles, never averages: a p50 of 40 ms with a p99 of 4 s means one request in a hundred is terrible, and a page that makes twenty calls hits that tail most of the time.

## Distributed traces

A **trace** is the full journey of one request; each step is a **span** with a start, a duration, attributes and a parent. Services pass the trace context to each other in the W3C `traceparent` header (and in Kafka message headers), so the gateway’s span, Ordering’s gRPC call and Inventory’s SQL query land in one tree, whatever language produced them.

Java and Python can be instrumented with no code changes; .NET, Node and Go need a few lines at startup. All five export **OTLP** to an **OpenTelemetry Collector**, which forwards to whatever backend you use (Jaeger, Tempo, Prometheus, Grafana, Datadog, Honeycomb, a cloud vendor). Switching vendors means changing the collector, not five codebases.

Add **manual spans** for important internal steps ("price order", "append to ledger") and set attributes such as `order.id` on the current span, so traces speak the domain’s language.

<Pitfall title="Cardinality explosions">
Metric labels with unbounded values (user id, order id, full URL with ids) create a separate time series per value and can take down a metrics backend. Use route templates (`/orders/{id}`), not raw paths, as labels; put ids in traces and logs instead.
</Pitfall>

## SLOs and alerting

An **SLO** (service level objective) states what "good" means for users, for example: 99.9% of checkout requests succeed within 1 second over 30 days. The remaining 0.1% is the **error budget**. Alert when the budget **burns** too fast (a fast burn pages someone; a slow burn opens a ticket), not on CPU or memory, which are causes, not symptoms. Error budgets also settle the eternal argument between shipping features and fixing reliability: when the budget is spent, reliability work comes first.

<InTheWild>
OpenTelemetry has become the default way to instrument services across languages, and most observability vendors ingest OTLP directly. In practice teams run a collector per cluster, sample traces (keeping all errors and slow requests), and build one dashboard per service with RED metrics, dependencies, saturation and SLO burn.
</InTheWild>

<InterviewLens>
"Users say checkout is slow sometimes. How do you find out why?" A strong answer: check the latency histogram (p99, not average) and SLO burn for the checkout route, open example slow traces to see which span dominates, follow the trace id into logs of that service, compare with deploys and dependency metrics (pool saturation, consumer lag, GC), form a hypothesis, fix, and confirm on the same graphs.
</InterviewLens>

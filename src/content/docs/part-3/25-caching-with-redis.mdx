SeatLock’s event pages are read thousands of times per minute and change a few times per day. Querying PostgreSQL for each view wastes the database on answers it already gave. Caching fixes that, and introduces the second hard problem in computer science: knowing when the cached answer is no longer true. This chapter covers where to cache, the patterns, the failure modes, and Redis as the shared cache for every stack.

## Where to cache

| Layer | Example | Shared across replicas | Invalidation |
| --- | --- | --- | --- |
| Client and CDN | `Cache-Control: public, max-age=60` | Yes, globally | TTL, purge API |
| In-process memory | A map with TTL | No | Per replica |
| Distributed cache | Redis | Yes | Explicit delete or TTL |
| Database | Its own buffer cache | n/a | Automatic |

Start at the outside: a public event page with `max-age=30` on a CDN removes most traffic before it reaches you. Use an in-process cache for small, rarely changing data (configuration, venue layouts). Use Redis when replicas must agree, or the data is too large to copy into every process.

## Cache-aside

The default pattern: read the cache, on a miss load from the database and store with a TTL, and on writes delete the key so the next read reloads it.

```go
func (s *Service) FindEvent(ctx context.Context, id string) (EventDTO, error) {
	key := "event:" + id + ":v1"
	if b, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
		var e EventDTO
		return e, json.Unmarshal(b, &e)
	}
	v, err, _ := s.group.Do(key, func() (any, error) { // one loader per key per process
		e, err := s.repo.LoadEvent(ctx, id)
		if err == nil {
			b, _ := json.Marshal(e)
			s.rdb.Set(ctx, key, b, 5*time.Minute)
		}
		return e, err
	})
	if err != nil {
		return EventDTO{}, err
	}
	return v.(EventDTO), nil
}
```
</Stack>

Notice the `:v1` in each key: when the cached shape changes, bump the version and old entries simply age out, with no flush during a deploy.

## Invalidation

There are only three strategies, and every system combines them:

- **TTL**: accept staleness up to N seconds. Simple and robust; pick N from what the business tolerates.
- **Delete on write**: after committing a change, delete the key. Precise, but every write path must remember it, and a crash between commit and delete leaves stale data until the TTL. Always keep a TTL as a backstop.
- **Write-through**: update the cache together with the database. Fresher, but more code and more ways to diverge.

<Pitfall title="Caching what must be exact">
SeatLock caches event descriptions and seat maps, but **never** seat availability for checkout. A cached "available" that is two seconds old sells a held seat. Cache data where staleness is harmless, and read the source of truth for decisions.
</Pitfall>

## Stampedes

When a hot key expires, every concurrent request misses and hits the database at the same moment. Three defences: **single-flight** (one loader per key, others wait, as Go’s `singleflight` and .NET’s `HybridCache` do), **early refresh** (reload slightly before expiry), and **jittered TTLs** (300 s ± 10 %) so many keys do not expire together after a deploy.

## Redis beyond caching

Redis is a data-structure server, and backends use it for more than cache entries: counters and sliding windows for **global rate limits**, sorted sets for leaderboards and delayed jobs, pub/sub for fan-out (Chapter 38), and as the store behind BullMQ, Celery and sessions. Treat it as memory with optional persistence: anything that must survive a failure belongs in PostgreSQL.

<InTheWild>
Distributed locks in Redis are a frequent source of subtle bugs: a lock with a TTL can expire while its holder is paused, and two processes then believe they hold it. If correctness depends on a lock, prefer the database (row locks, unique constraints, advisory locks) or a fencing token. Use Redis locks only to reduce duplicate work, not to guarantee correctness.
</InTheWild>

<InterviewLens>
"Add caching to this read-heavy endpoint." A strong answer asks how stale the data may be, picks the outermost layer that works (HTTP caching or CDN first), uses cache-aside with a TTL and delete-on-write, versions keys, includes the user or tenant in keys for personal data, protects against stampedes, measures hit rate, and never caches the data used for decisions that must be exact.
</InterviewLens>

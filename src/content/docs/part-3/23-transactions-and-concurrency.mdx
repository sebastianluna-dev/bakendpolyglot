## ACID without the slogans

A **transaction** groups statements so they succeed or fail together. **Atomicity**: all or nothing. **Consistency**: constraints hold at commit. **Durability**: once committed, it survives a crash. The interesting letter is **I**, isolation: how much concurrent transactions see of each other. Full isolation is expensive, so databases offer levels, and the default is weaker than most people assume.

## Isolation levels and their anomalies

| Anomaly | What happens | Read Committed | Repeatable Read | Serializable |
| --- | --- | --- | --- | --- |
| Dirty read | See another transaction’s uncommitted data | Prevented | Prevented | Prevented |
| Non-repeatable read | Read a row twice, get different values | Possible | Prevented | Prevented |
| Phantom | Re-run a range query, get new rows | Possible | Prevented in Postgres | Prevented |
| Lost update | Two read-modify-writes, one is lost | Possible | Detected (error) | Prevented |
| Write skew | Two transactions each keep a rule true alone, break it together | Possible | Possible | Prevented |

PostgreSQL defaults to **Read Committed**. Its **Repeatable Read** is snapshot isolation, and its **Serializable** level detects dangerous interleavings and aborts one transaction with SQLSTATE `40001`, which your code must retry. Other databases differ: MySQL’s InnoDB defaults to Repeatable Read with different semantics, so never assume.

The naive code reads the seat, checks `status == 'available'` in the application, and writes `status = 'held'`. Under Read Committed both transactions pass the check before either writes. There are three reliable fixes, from simplest to most general.

### 1. Make the write conditional

Put the check inside the write so the database evaluates it atomically:

```sql
UPDATE seats SET status = 'held', held_by = $2, hold_expires_at = now() + interval '10 minutes'
WHERE id = $1 AND status = 'available'
RETURNING id;
```

Zero rows returned means someone else got it. This is the cheapest fix and covers most "claim a thing" operations, including holding several seats in one statement.

### 2. Optimistic locking

When the change is computed in application code (a price recalculated, several fields edited), add a `version` column, read it with the data, and make the write conditional on it being unchanged. Every ORM supports this natively:

<FromTS>
Node’s single thread does not save you here. Two requests interleave at every `await`, and the race lives in the database, not in your process. The same is true in every stack in this book, and doubly so once you run more than one replica.
</FromTS>

### 3. Pessimistic locking

Lock the rows first, then decide. Other transactions trying to lock the same rows wait until you commit:

```sql
BEGIN;
SELECT id, status FROM seats WHERE event_id = $1 AND id = ANY($2) FOR UPDATE;
-- check in code, then:
UPDATE seats SET status = 'held', held_by = $3 WHERE id = ANY($2);
COMMIT;
```

Every stack exposes it: `FOR UPDATE` in raw SQL, `@Lock(PESSIMISTIC_WRITE)` in Spring Data, `select_for_update()` in Django, a raw query or `FromSql` in EF Core. Add `SKIP LOCKED` to grab whatever rows are free instead of waiting, which makes "give me any two seats in row F" and job queues (Chapter 24) fast under contention.

## Choosing

| Situation | Choose |
| --- | --- |
| Claim or decrement with a simple condition | Conditional `UPDATE … WHERE` |
| Edits computed in code, low contention | Optimistic locking (version) |
| Hot rows, many writers at once | Pessimistic `FOR UPDATE`, short transactions |
| Pick any free rows | `FOR UPDATE SKIP LOCKED` |
| Invariants across many rows (write skew) | Serializable isolation with retries, or a constraint |

<Pitfall title="Long transactions and deadlocks">
Locks are held until commit, so never call an external API, send an email or wait on user input inside a transaction. Keep transactions short, and acquire locks in a consistent order (for example by seat id) so two transactions cannot wait on each other forever. Databases detect deadlocks and kill one transaction; your code must handle that error like a conflict.
</Pitfall>

<InTheWild>
Ticketing, inventory and booking systems all solve this problem, and most of them combine the techniques: a short "hold" claimed with a conditional update or `SKIP LOCKED`, an expiry job that releases stale holds, unique constraints as the final guard, and idempotency keys so retried checkouts do not double-charge (next chapter).
</InTheWild>

<InterviewLens>
"Design checkout for a sold-out concert." A strong answer names the race, picks a lock strategy for the contention level (conditional updates or SKIP LOCKED for seat claims, optimistic versions for edits), keeps transactions short, adds a hold with expiry so abandoned carts free seats, and adds an idempotency key for retries. It mentions what the database guarantees at its default isolation level.
</InterviewLens>

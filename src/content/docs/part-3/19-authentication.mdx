This chapter covers the two families of authentication you will meet in every stack, sessions and tokens, the rules for passwords, and how each framework validates a token on every request.

A **session** is a random identifier in a cookie that points to state stored on the server (Redis or a table). A **token** is a signed document that carries its own claims; the server verifies the signature and reads the claims without a lookup. Neither is "more secure": sessions are simpler for a single web app and its own backend; tokens shine when many services must verify the same caller, which is why SeatLock’s API accepts tokens from an identity provider (Chapter 20).

## Passwords, if you must store them

The best password storage is none: delegate login to an identity provider. When you must store passwords, the rules are short and non-negotiable:

- Hash with a slow, salted, memory-hard algorithm: **Argon2id** first, **bcrypt** as the common alternative. Every stack has a maintained library or a built-in (`PasswordHasher` in ASP.NET Identity, `PasswordEncoder` in Spring Security, Django’s hashers).
- Never encrypt passwords (encryption is reversible), never use a fast hash (SHA-256 is designed to be fast, which helps attackers).
- Rate-limit login attempts, return the same error for unknown user and wrong password, and support multi-factor authentication.

## JWTs, correctly

A **JWT** is three base64url parts: a header (algorithm, key id), a payload of claims, and a signature. It is signed, not encrypted: never put anything secret in it.

```json
{ "iss": "https://id.seatlock.dev", "sub": "user_8121", "aud": "seatlock-api",
  "exp": 1794510000, "iat": 1794509100, "scope": "holds:write orders:read", "roles": ["customer"] }
```

Validation is where most bugs are. A service must:

1. Verify the signature with a key it trusts, looked up by `kid` from the issuer’s JWKS endpoint.
2. **Pin the algorithm** (for example RS256 or ES256); never accept `none` or let the token choose.
3. Check `exp` (with a small clock skew), `iss` (the issuer you trust) and `aud` (this API).
4. Only then read `sub`, scopes and roles.

const JWKS = createRemoteJWKSet(new URL(`${ISSUER}/protocol/openid-connect/certs`));

@Injectable()
export class JwtGuard implements CanActivate {
  async canActivate(ctx: ExecutionContext) {
    const req = ctx.switchToHttp().getRequest();
    const token = req.headers.authorization?.replace(/^Bearer /, '');
    if (!token) throw new UnauthorizedException();
    const { payload } = await jwtVerify(token, JWKS, { issuer: ISSUER, audience: 'seatlock-api', algorithms: ['RS256'] })
      .catch(() => { throw new UnauthorizedException(); });
    req.user = payload;
    return true;
  }
}

// …
func authenticate(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		raw := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
		tok, err := jwt.Parse(raw, jwks.Keyfunc,
			jwt.WithValidMethods([]string{"RS256"}), jwt.WithIssuer(issuer),
			jwt.WithAudience("seatlock-api"), jwt.WithExpirationRequired())
		if err != nil || !tok.Valid {
			writeProblem(w, Problem{Status: 401, Title: "Unauthenticated"})
			return
		}
		next.ServeHTTP(w, r.WithContext(withClaims(r.Context(), tok.Claims)))
	})
}

ASP.NET Core and Spring discover the keys from the issuer’s metadata and do every check for you, given the right configuration. Nest, Go and FastAPI use small libraries; the checks are explicit, which makes them easy to review.

## Access tokens, refresh tokens and logout

Keep **access tokens short-lived** (5 to 15 minutes) so a stolen one expires soon. A **refresh token**, stored server-side by the identity provider and revocable, obtains new access tokens. With **rotation**, every refresh returns a new refresh token and invalidates the old one; if an old one is used again, the provider revokes the whole family, because it has probably been stolen.

Logout then means revoking the refresh token and letting the short access token expire. If you need instant revocation of access tokens (an employee is fired, an account is compromised), add a small denylist of token ids checked at the gateway, or use opaque tokens checked by introspection.

<Pitfall title="Tokens in localStorage">
Anything JavaScript can read, an XSS bug can steal. For browser apps, the safest pattern is a **backend for frontend** (BFF): the browser holds an `HttpOnly`, `Secure`, `SameSite` session cookie for the BFF, and the BFF holds the tokens and calls APIs. Mobile apps and services, which have no cookies or XSS, use bearer tokens directly.
</Pitfall>

<InTheWild>
Most companies no longer build login themselves. They run an identity provider (Keycloak, Auth0, Okta, Microsoft Entra ID, AWS Cognito) and their APIs only validate tokens. As a backend engineer you are expected to configure token validation correctly, understand the claims, and know when sessions are the simpler answer.
</InTheWild>

<InterviewLens>
"Sessions or JWTs?" A strong answer refuses the false choice: sessions for a first-party web app with its own backend (simple, instantly revocable), tokens from an identity provider when several APIs or clients need to verify identity, with short access tokens, rotating refresh tokens, cookies via a BFF in browsers, and correct validation of signature, algorithm, exp, iss and aud.
</InterviewLens>

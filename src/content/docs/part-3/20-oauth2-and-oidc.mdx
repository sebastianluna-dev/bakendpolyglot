Chapter 19 had SeatLock validate tokens from an identity provider. This chapter explains where those tokens come from. **OAuth2** is a framework for delegated access: a user lets an app call an API on their behalf without giving the app their password. **OpenID Connect** (OIDC) adds a standard identity layer on top. Together they power "Sign in with…" buttons, mobile logins and service-to-service auth.

## Four roles

- **Resource owner**: the user.
- **Client**: the app acting for the user (SeatLock’s web or mobile app).
- **Authorization server**: issues tokens after authenticating the user (Keycloak in this book).
- **Resource server**: the API that accepts access tokens (SeatLock’s API).

The client creates a random **code verifier** and sends its hash, the **code challenge**, in step 2. In step 6 it sends the verifier itself. An attacker who intercepts the code in step 4 cannot redeem it without the verifier. The browser only ever sees a short-lived, single-use code; the tokens go straight from Keycloak to the client.

## Client credentials for services

When there is no user, such as a nightly job that releases expired seat holds through the API, a confidential client authenticates as itself:

```http
POST /realms/seatlock/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=hold-reaper&client_secret=…&scope=holds:admin
```

The response is an access token whose `sub` is the client, with the scopes it was granted. Cache it until shortly before `exp`; do not request a new token per call.

## Scopes, roles and claims

**Scopes** describe what a client may do on a user’s behalf (`holds:write`), and the user can see and consent to them. **Roles** describe what the user is (`customer`, `box-office`). Identity providers put both in the access token, and your API’s authorization (Chapter 21) reads them. Keep scopes coarse and stable; put fine-grained rules in the API.

## OpenID Connect

OIDC standardises three things OAuth2 left open:

- The **ID token**: a JWT for the client, saying who signed in (`sub`, `email`, `name`, `auth_time`).
- The **userinfo** endpoint, for more profile claims.
- **Discovery**: `/.well-known/openid-configuration` lists every endpoint, supported algorithm and the JWKS URL. This is what `Authority` in ASP.NET and `issuer-uri` in Spring read.

<Pitfall title="Using the wrong token">
APIs accept **access tokens** issued for them (`aud` is the API). Clients use **ID tokens** to know who signed in. Sending an ID token to an API, or using an access token in the client to display the user, mixes the two and breaks as soon as the identity provider changes token formats.
</Pitfall>

## Keycloak for local development

Every companion app that needs identity runs Keycloak in Docker Compose with a realm file committed to the repository: a `seatlock` realm, a public client for the web app with PKCE, a confidential client for the hold reaper, two roles and three test users. Tests get tokens from it exactly as production clients will.

```yaml title="compose.yaml (excerpt)"
keycloak:
  image: quay.io/keycloak/keycloak:26.0
  command: start-dev --import-realm
  environment:
    KC_BOOTSTRAP_ADMIN_USERNAME: admin
    KC_BOOTSTRAP_ADMIN_PASSWORD: admin
  volumes: ["./keycloak/seatlock-realm.json:/opt/keycloak/data/import/seatlock-realm.json"]
  ports: ["8081:8080"]
```

<InTheWild>
In companies, you rarely run the authorization server yourself; a platform team or a SaaS provider does. Your daily work is registering clients, choosing flows and scopes, validating tokens in services, and debugging token claims. Paste a token into a JWT debugger when something fails: wrong `aud` and expired `exp` explain most 401s.
</InTheWild>

## 1. URL shortener

**Requirements.** Create a short link for a long URL; redirect fast; optional expiry and analytics. Reads dominate: about 100 redirects per creation.

**Numbers.** 100 million new links a month is roughly 40 writes per second and 4,000 redirects per second on average, with peaks several times higher. Five years of links at 500 bytes each is about 3 TB.

**Design.** A stateless API behind a load balancer; a key-value or relational store mapping code to URL; a cache (Redis or the CDN) in front of redirects, since popular links are read millions of times; analytics events sent to a queue, never written on the redirect path.

**Decisions.** Codes: seven base62 characters give about 3.5 trillion values. Generate them from a counter with ranges handed out to each instance (no collisions, but predictable, so shuffle them) or randomly with a unique constraint and retry on collision. Use `302` if you need analytics on every click, `301` if you want browsers to cache. Block malicious URLs at creation.

## 2. Distributed rate limiter

**Requirements.** Limit each API key to N requests per window across all instances; add little latency; fail open or closed by policy.

**Design.** A token bucket or sliding window per key in Redis, updated atomically with a Lua script (read, refill, decrement, return in one round trip). Enforce it at the API gateway so services stay simple. Return `429` with `Retry-After` and rate-limit headers.

**Decisions.** If Redis is down, fail open for most APIs (availability) but closed for login and payments (security). Keep a small local limiter as a first line to absorb abusive bursts without touching Redis. Shard keys across a Redis cluster; hot keys from one huge customer may need their own limits.

## 3. Chat

**Requirements.** One-to-one and group chat, delivery and read receipts, history, presence, online and offline users.

**Numbers.** 10 million daily users, 40 messages each, is 400 million messages a day, about 5,000 per second on average; concurrent connections in the low millions.

**Design.** Pulse’s architecture, scaled: connection servers holding WebSockets, routing through a pub/sub layer keyed by user or conversation; messages persisted **before** delivery in a store partitioned by conversation id (a wide-column store suits this write-heavy, time-ordered pattern); push notifications for offline users through a queue.

**Decisions.** Ordering per conversation with a sequence number assigned by the conversation’s partition. Delivery is at-least-once with client-side deduplication by message id. Presence is approximate (heartbeats with expiry), broadcast only to contacts who are online.

## 4. News feed

**Requirements.** Users follow others and see a ranked feed of recent posts; posting is rare, reading is constant.

**Design.** Posts in a store keyed by author; each user’s feed precomputed as a capped list of post ids in Redis. On post, a queue triggers workers that push the id into each follower’s feed (**fan-out on write**). Accounts with huge followings are skipped, and their recent posts are merged at read time (**fan-out on read**). Ranking runs on the merged candidates.

**Decisions.** Feeds hold ids, not content, so edits and deletions apply everywhere; content is fetched in batch and cached. Inactive users’ feeds are not maintained and are rebuilt on their next visit.

## 5. Ticketing

**Requirements.** Sell seats for high-demand events without overselling; survive traffic spikes at on-sale time.

**Design.** SeatLock (Chapter 27): atomic holds with expiry by conditional update, checkout with idempotency keys, payment confirmation by webhook, a reaper job. For spikes, add a **virtual waiting room** that admits users at a rate the hold service can handle, and serve event pages from the CDN.

**Decisions.** Seat availability is never cached for decisions. Partition hot events onto dedicated database capacity. Measure success with invariants (no seat in two paid orders), not just with HTTP status codes.

## 6. Payments

**Requirements.** Charge customers through external providers, never lose or duplicate money, reconcile with the provider and the bank.

**Design.** A **double-entry ledger**, append-only: every movement is a set of entries that sum to zero, and balances are derived (Parcel’s Payments service event-sources exactly this). Idempotency keys end to end: from the client to your API, and from your API to the provider. Webhooks verified and deduplicated; a state machine per payment (`created → authorised → captured → refunded`). Daily **reconciliation** jobs compare your ledger with provider and bank reports and raise discrepancies.

**Decisions.** Strong consistency and serialisable transactions inside the ledger; asynchronous everything else. Every external call can time out with an unknown outcome, so query the provider by idempotency key before retrying.

## 7. Notifications

**Requirements.** Send email, SMS and push notifications triggered by many services, respecting user preferences, quiet hours and rate limits per channel.

**Design.** Services publish notification requests to a queue; a notification service checks preferences, renders templates, deduplicates by key, and sends through per-channel workers with their own provider integrations, retries and dead-letter queues. Delivery status comes back by webhooks and is stored for support.

**Decisions.** Separate queues per channel and priority, so a bulk marketing send never delays a password-reset code. Idempotency per notification key, because users notice duplicates immediately.

<Pitfall title="Reciting a design from memory">
Interviewers change one requirement on purpose ("now it must work across three regions", "now reads must be consistent") to see if you reason or recite. Tie every component back to a requirement or a number, and the change becomes a conversation, not a trap.
</Pitfall>

<InTheWild>
Real systems at these companies are far messier than any case study, with history, constraints and partial migrations. What carries over is the habit: start from requirements and numbers, choose the simplest design that meets them, and know which part will break first as load grows.
</InTheWild>

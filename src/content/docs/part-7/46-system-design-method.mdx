## Four steps

**1. Requirements (5 minutes).** Ask before drawing. Functional: what must users do? Non-functional: how many users, reads versus writes, latency targets, consistency needs ("can a user see a stale balance?"), availability, data retention, regions. Write them down and agree on what is out of scope.

**2. Estimates (5 minutes).** Turn the numbers into requests per second, storage and bandwidth, with round figures. One day has roughly 100,000 seconds (86,400), which makes the arithmetic easy: 10 million requests a day is about 100 per second on average, and you plan for a peak of 3 to 10 times that.

**3. High-level design (15 minutes).** Draw clients, edge (CDN, load balancer, gateway), services, data stores, caches, queues. Walk one request of each important kind through it. Define the main APIs and the data model.

**4. Deep dives (15 minutes).** Pick the two or three hardest parts, or let the interviewer pick, and go deep: the data model at scale, the hot path, consistency, failure modes. State trade-offs explicitly: "I choose X, which costs Y, because requirement Z matters more."

## Numbers worth remembering

| Operation | Rough time |
| --- | --- |
| Main memory reference | 100 ns |
| Read 1 MB sequentially from memory | 10–50 µs |
| Round trip within a data centre | 0.5 ms |
| Read 1 MB from SSD | ~1 ms |
| Simple indexed database query (warm) | 1–5 ms |
| Round trip across a continent | 30–80 ms |
| Round trip across an ocean | 100–150 ms |

Orders of magnitude are what matter: memory is a thousand times faster than a network hop, and a network hop is a hundred times faster than crossing an ocean. A single well-tuned PostgreSQL primary handles thousands to tens of thousands of simple transactions per second; Redis handles on the order of a hundred thousand operations per second per node.

## Scaling vocabulary

**Vertical and horizontal.** Scale up (a bigger machine) until it stops being simple or affordable; scale out (more machines) when you must. Stateless services scale out trivially behind a load balancer; state is where the work is.

**Load balancing.** Layer 4 balances connections, layer 7 balances requests and can route by path or header. Algorithms: round robin, least connections, consistent hashing when requests should land on the same node (caches, WebSockets).

**Replication.** A primary takes writes; **read replicas** serve reads. Asynchronous replication means replicas lag, so a user may not see their own write if the next read goes to a replica: route read-your-own-writes to the primary.

**Partitioning (sharding).** Split data across databases by a **shard key**. Queries that include the key hit one shard; queries that do not fan out to all of them. Choose the key from the dominant access pattern (tenant id for B2B systems, user id for social ones), and plan for hot keys (a celebrity, a big tenant).

**CAP and PACELC.** When the network partitions, a replicated store must either refuse some requests to stay consistent (CP) or keep answering with possibly stale data (AP). **PACELC** adds the everyday case: **else**, when there is no partition, you still trade **latency** against **consistency**. Most real systems pick per operation: a balance must be consistent; a like counter can be eventually consistent.

**Consistency models**, from strongest to weakest: linearizable (every read sees the latest write), sequential, causal (cause before effect, such as a reply after its message), read-your-writes, eventual. Name the one each feature needs.

<Pitfall title="Drawing boxes without numbers">
A design with Kafka, Redis, sharding and microservices for 50 requests per second is not senior; it is expensive. Let the estimates decide: if one PostgreSQL instance with a replica fits the numbers for five years, say so, and explain what you would change at ten times the load.
</Pitfall>

<InterviewLens>
The interview is the method. Interviewers look for requirement questions before solutions, numbers that drive choices, a clean high-level design walked through with real requests, depth on the hard parts, explicit trade-offs, and failure handling. Saying "I don’t know, but here is how I would find out" is better than bluffing.

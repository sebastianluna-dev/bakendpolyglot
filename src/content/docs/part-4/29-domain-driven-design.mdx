Hexagonal architecture says to keep the domain in the middle. **Domain-Driven Design** (DDD) says how to find the right domain, and where one domain ends and the next begins. Its strategic half draws boundaries between parts of a business; its tactical half gives you building blocks for the code inside each boundary. Parcel’s service split in Part V comes directly from this chapter.

## Strategic design: bounded contexts

In a real business, the same word means different things to different teams. To the catalog team, a **product** has a description, images and a price. To the warehouse, a product is a SKU with stock levels per location. To shipping, it is a parcel with a weight and dimensions. Forcing one `Product` class to serve all three produces a god object nobody can change.

A **bounded context** is a boundary inside which one model and one vocabulary are consistent: the **ubiquitous language** that domain experts and code share. Parcel has five:

A **context map** like this one shows each context, who depends on whom, and how they integrate: synchronous queries for data needed now (Ordering asks Catalog for the current price), and domain events for facts others react to (Inventory reserves stock when it hears `OrderPlaced`). Each context owns its data; nobody reads another context’s tables.

Bounded contexts are the best starting point for service boundaries, but they are not the same thing: one service can host several small contexts, and Chapter 31 argues that it often should at first.

## Tactical design: the building blocks

Inside a context, DDD offers a small vocabulary:

| Block | What it is | Parcel example |
| --- | --- | --- |
| Entity | Has identity that persists as attributes change | `Order`, `Customer` |
| Value object | Defined only by its values; immutable | `Money`, `Address`, `Sku` |
| Aggregate | A cluster of objects changed as one unit, with a root | `Order` with its `OrderLine`s |
| Domain event | A fact that happened, past tense | `OrderPlaced` |
| Repository | Loads and saves whole aggregates | `OrderRepository` |
| Domain service | Logic that belongs to no single entity | `PricingPolicy` |

The **aggregate** is the important one. It is a **consistency boundary**: every rule that must hold immediately ("an order’s total equals the sum of its lines", "you cannot add lines after the order is placed") is enforced by the **root**, and nothing outside may change the inside directly. Rules that span aggregates ("stock must not go negative across all orders") are enforced eventually, through events, or by the aggregate that owns the data.

<Stack id="nest" lib="TypeScript">
```ts
export class Order {
  private readonly lines: OrderLine[] = [];
  private status: 'draft' | 'placed' = 'draft';
  readonly events: DomainEvent[] = [];

  constructor(readonly id: OrderId, readonly customerId: CustomerId) {}

  addLine(sku: Sku, qty: number, unitPrice: Money) {
    if (this.status !== 'draft') throw new OrderNotEditable(this.id);
    if (qty < 1 || qty > 10) throw new InvalidQuantity(qty);
    this.lines.push(new OrderLine(sku, qty, unitPrice));
  }

  place() {
    if (this.lines.length === 0) throw new EmptyOrder(this.id);
    this.status = 'placed';
    this.events.push(new OrderPlaced(this.id, this.total()));
  }

  total(): Money { return this.lines.reduce((sum, l) => sum.add(l.subtotal()), Money.zero('EUR')); }
}
```

```csharp
    private readonly List<OrderLine> _lines = [];
    private readonly List<IDomainEvent> _events = [];
    public OrderId Id { get; }
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public IReadOnlyList<IDomainEvent> Events => _events;

    public void AddLine(Sku sku, int qty, Money unitPrice)
    {

        if (qty is < 1 or > 10) throw new InvalidQuantity(qty);
        _lines.Add(new OrderLine(sku, qty, unitPrice));
    }

    public void Place()
    {
        if (_lines.Count == 0) throw new EmptyOrder(Id);
        Status = OrderStatus.Placed;
        _events.Add(new OrderPlaced(Id, Total));
```

```kotlin
class Order(val id: OrderId, val customerId: CustomerId) {
    private val lines = mutableListOf<OrderLine>()
    var status = OrderStatus.DRAFT; private set
    val events = mutableListOf<DomainEvent>()

    fun addLine(sku: Sku, qty: Int, unitPrice: Money) {
        check(status == OrderStatus.DRAFT) { "Order $id is not editable" }
        require(qty in 1..10) { "Invalid quantity $qty" }
        lines += OrderLine(sku, qty, unitPrice)
    }

    fun place() {
        if (lines.isEmpty()) throw EmptyOrder(id)
        status = OrderStatus.PLACED
        events += OrderPlaced(id, total())
    }

    fun total(): Money = lines.fold(Money.zero("EUR")) { sum, l -> sum + l.subtotal() }
}
```

```go
	if o.status != Draft {
		return ErrOrderNotEditable
	}
	if qty < 1 || qty > 10 {
		return fmt.Errorf("%w: %d", ErrInvalidQuantity, qty)
	}
	o.lines = append(o.lines, OrderLine{Sku: sku, Qty: qty, UnitPrice: unitPrice})
	return nil

func (o *Order) Place() error {
	if len(o.lines) == 0 {
		return ErrEmptyOrder
	}
	o.status = Placed
	o.events = append(o.events, OrderPlaced{OrderID: o.id, Total: o.Total()})
	return nil
}
```

```python
class Order:
    def __init__(self, id: OrderId, customer_id: CustomerId) -> None:
        self.id, self.customer_id = id, customer_id
        self._lines: list[OrderLine] = []
        self.status = OrderStatus.DRAFT
        self.events: list[DomainEvent] = []

    def add_line(self, sku: Sku, qty: int, unit_price: Money) -> None:
        if self.status is not OrderStatus.DRAFT:
            raise OrderNotEditable(self.id)
        if not 1 <= qty <= 10:
            raise InvalidQuantity(qty)
        self._lines.append(OrderLine(sku, qty, unit_price))

    def place(self) -> None:
        if not self._lines:
            raise EmptyOrder(self.id)
        self.status = OrderStatus.PLACED
        self.events.append(OrderPlaced(self.id, self.total()))

    def total(self) -> Money:
        return sum((l.subtotal() for l in self._lines), Money.zero("EUR"))
```

Every version keeps its state private, exposes behaviour named in the domain’s language, and records events instead of calling other systems. The repository saves the order and, in the same transaction, the events to an outbox (Chapter 34), so they are published reliably.

<Pitfall title="Anaemic domain models">
Entities that are only getters and setters, with all rules in "service" classes, lose the main benefit of an aggregate: one place that guarantees its invariants. If `order.status = 'placed'` can be written from anywhere, the rule "only place non-empty orders" lives wherever someone remembered it.
</Pitfall>

<FromTS>
Value objects such as `Money` replace "primitive obsession": passing `amount: number, currency: string` pairs around invites adding euros to dollars. A small immutable type with `add` that checks currencies removes a whole class of bugs. Records in C#, Java and Kotlin, frozen dataclasses in Python and plain structs in Go make them cheap.
</FromTS>

<InTheWild>
Most teams use DDD selectively: strategic design to agree on boundaries and vocabulary (often in an event-storming workshop with domain experts), tactical patterns only in the contexts with real rules. A context that is really CRUD over a few tables does not need aggregates and domain events.
</InTheWild>

<InterviewLens>
"How would you split this system into services?" A strong answer starts with bounded contexts discovered from the business language and workflows, draws a context map with upstream and downstream relationships, keeps data owned per context, sizes aggregates around invariants that must hold immediately, and treats services as a deployment decision made after the boundaries are understood.
</InterviewLens>

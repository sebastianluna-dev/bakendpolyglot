Once a system has several services and a deliberate structure, two new kinds of failure appear. A service changes a response field and a consumer in another repository breaks in production. Or, over months, convenient imports quietly erase the boundaries Chapters 28 to 31 drew. This chapter adds tests for both: **contract tests** between services and **architecture tests** inside them, plus two techniques that sharpen the suites you already have.

## Contract tests between services

End-to-end tests across five services are slow and flaky, and they find contract breaks late. **Consumer-driven contract testing** finds them in each service’s own CI. With Pact, the consumer (Parcel’s gateway) records what it sends and which fields it reads:

```ts
const provider = new PactV3({ consumer: 'parcel-gateway', provider: 'parcel-catalog' });

provider
  .given('product BK-1 exists')
  .uponReceiving('a request for product BK-1')
  .withRequest({ method: 'GET', path: '/products/BK-1' })
  .willRespondWith({
    status: 200,
    body: { sku: 'BK-1', name: like('Dune'), price: { amount: like(1800), currency: 'EUR' } },
  });

await provider.executeTest(async (mock) => {
  const product = await catalogClient(mock.url).getProduct('BK-1');
  expect(product.sku).toBe('BK-1');
});
```

That produces a contract file, published to a broker. The provider (Catalog, in FastAPI) runs a **verification** in its CI that replays every consumer’s expectations against the real service. If Catalog renames `name` to `title`, its build fails and names the consumer it would break. Pact has libraries for all five stacks, which is exactly what a polyglot system needs.

Contract tests complement, not replace, the OpenAPI document: the document says what the provider offers; contracts say what consumers actually depend on, so providers know what they can change freely.

## Architecture tests

Diagrams do not stop imports. **Architecture tests** do: they read the code’s dependencies and fail the build when a rule is broken. Here is "the order core must not depend on adapters or frameworks" in each stack:

```js
    from: { path: '^src/orders/core' },
```

```csharp
public void Core_does_not_depend_on_infrastructure()

        .ShouldNot()
        .HaveDependencyOnAny("Microsoft.AspNetCore", "Microsoft.EntityFrameworkCore", "Parcel.Payments.Infrastructure")
        .GetResult();
    Assert.True(result.IsSuccessful);
}
```
</Stack>
<Stack id="kotlin" lib="ArchUnit">
```kotlin
@AnalyzeClasses(packages = ["parcel.orders"])

    @ArchTest
    val coreIsPure: ArchRule = noClasses().that().resideInAPackage("..core..")
        .should().dependOnClassesThat()
        .resideInAnyPackage("..adapters..", "org.springframework..", "jakarta.persistence..")
}
```
</Stack>

Start with two or three rules that protect what matters (core purity, no cross-module data access, no cycles between modules) and add more only when a real erosion happens. In Go, remember that the compiler already enforces `internal/` packages for free.

## Test doubles, precisely

Teams argue about mocks partly because they use the word for everything. The precise vocabulary helps in code review:

| Double | What it does | Use it for |
| --- | --- | --- |
| Dummy | Fills a parameter, never used | Satisfying a signature |
| Stub | Returns canned answers | Driving the code down a path |
| Fake | A working, lightweight implementation | In-memory repository, fake payment provider |
| Spy | Records calls for later assertions | Checking that an event was published |
| Mock | Pre-programmed expectations that fail if unmet | When the interaction is the behaviour |

Prefer **fakes** for driven ports: a `FakePaymentGateway` written once, shared by many tests, and checked against the real adapter with a small contract test of its own, so the fake cannot drift.

## Testing event-driven code

When services communicate through events (Part V), test three things separately: the producer writes the right event to its outbox in the same transaction as the state change; the consumer handles an event correctly **and idempotently** (feed it twice, assert one effect); and the event schema is compatible with consumers, using the same contract-testing idea for messages, which Pact also supports.

## Mutation testing

Coverage says which lines ran, not whether tests would notice them being wrong. **Mutation testing** changes the code (flips `<` to `<=`, removes a call, returns a constant) and reruns the tests; a mutant that survives shows code whose behaviour is not really checked. Tools: Stryker (TypeScript and C#), PIT (Java and Kotlin), mutmut (Python), and community tools for Go. It is slow, so run it on the domain core, nightly or before releases, not on every commit.

<Pitfall title="Contract tests as integration tests">
Pact contracts should capture what the consumer needs, not every field and every business scenario of the provider. Over-specified contracts break on harmless changes and teams start ignoring them. Use flexible matchers (`like`, `eachLike`), and keep business-rule testing in the provider’s own suite.
</Pitfall>

<InTheWild>
Polyglot organisations lean on contract testing because no single team can run everyone’s end-to-end suite. A typical CI pipeline for a provider runs its unit and integration tests, verifies consumer contracts from the broker, and asks the broker whether the version is safe to deploy against what is in production ("can I deploy?").
</InTheWild>

<InterviewLens>
"How do you stop one team’s API change from breaking another team’s service?" A strong answer: versioned contracts (OpenAPI or schemas), consumer-driven contract tests verified in the provider’s CI with a broker, additive changes by default, deprecation windows for breaking ones, and architecture tests to keep each service’s internal boundaries honest.
</InterviewLens>

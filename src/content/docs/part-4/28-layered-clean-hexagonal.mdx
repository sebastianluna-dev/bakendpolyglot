Part IV builds the first half of **Parcel**, an e-commerce order pipeline whose services are written in different languages. Before splitting anything into services, we need to agree on how one service is organised inside. This chapter compares the three common shapes, layered, clean and hexagonal, which are really one idea seen from different angles: keep business rules independent of frameworks, databases and transports.

## From layers to hexagons

The **layered** architecture you used in Shelfwise stacks presentation on top of business logic on top of data access. It is simple and familiar, with one flaw: the business layer usually depends on the data layer, so domain code ends up importing ORM types and the database shape leaks upwards.

**Clean** and **hexagonal** (ports and adapters) architectures fix that by inverting the last dependency. The core defines interfaces for what it needs, and the database code implements them:

- A **port** is an interface owned by the core: `OrderRepository`, `PaymentGateway`, or the use case `PlaceOrder` itself.
- A **driving adapter** calls into the core: an HTTP controller, a message consumer, a CLI.
- A **driven adapter** is called by the core through a port: the Postgres repository, the payment provider client, an email sender.

The **dependency rule**: source code dependencies point inwards. The domain imports nothing from ASP.NET, Spring, Express, `net/http` or Django; adapters import the domain.

## A port and its adapter, five ways

Parcel’s order service needs to charge a payment. The core declares what it needs; an adapter at the edge talks to the provider.

<FiveStacks note="The PaymentGateway port and a provider adapter">
<Stack id="nest" lib="TypeScript">
```ts
// core/ports.ts — owned by the domain
export interface PaymentGateway {
  charge(orderId: OrderId, amount: Money, idempotencyKey: string): Promise<PaymentRef>;
}
export const PAYMENT_GATEWAY = Symbol('PaymentGateway');

// adapters/acme-pay.gateway.ts — depends on the core, not the reverse
@Injectable()
export class AcmePayGateway implements PaymentGateway {
  constructor(private readonly http: HttpService) {}
  async charge(orderId: OrderId, amount: Money, key: string) { /* call the provider */ }
}
// module: { provide: PAYMENT_GATEWAY, useClass: AcmePayGateway }
```
</Stack>

```python
# orders/core/ports.py
class PaymentGateway(Protocol):
    async def charge(self, order_id: OrderId, amount: Money, idempotency_key: str) -> PaymentRef: ...

# orders/adapters/acme_pay.py
class AcmePayGateway:              # satisfies the Protocol structurally
    def __init__(self, client: httpx.AsyncClient) -> None:
        self._client = client
    async def charge(self, order_id: OrderId, amount: Money, idempotency_key: str) -> PaymentRef: ...
```

The payoff shows in tests and change. The `PlaceOrder` use case is unit-tested with a fake gateway in milliseconds. Switching payment providers, or adding a message consumer that places orders from a queue, touches one adapter and no business code.

<FromTS>
Go’s and Python’s structural typing make ports almost free: the adapter satisfies the interface without naming it. C#, Java and Kotlin need explicit `implements`, and C# teams usually enforce the rule with separate projects, so the compiler stops the core from referencing infrastructure at all.
</FromTS>

## Folders that show the architecture

A package structure should make the architecture visible. Parcel’s order service, in any stack:

```text
orders/
├── core/            # entities, value objects, domain errors, ports, use cases
├── adapters/
│   ├── http/        # controllers, DTOs, Problem Details mapping
│   ├── postgres/    # repository implementations, SQL, migrations
│   └── acmepay/     # payment gateway client
└── main / bootstrap # wiring: the only place that knows every piece
```

Prefer packaging **by feature** at the top level (`orders/`, `payments/`), and by layer inside each feature, over one global `controllers/`, `services/`, `repositories/` split that scatters every feature across the codebase.

<Pitfall title="Architecture as ceremony">
Ports for every table, mappers between identical classes, and use-case objects that only forward a call make simple code slow to change. Apply the full structure where rules and integrations justify it, such as Parcel’s orders and payments, and keep CRUD-heavy corners as plain handler, service, repository.
</Pitfall>

<InTheWild>
You will hear all three names, often used interchangeably, plus "onion architecture". What teams actually agree on is the dependency rule and keeping frameworks out of the domain. Spring Modulith, .NET solution templates and many Go project layouts encode some version of it.
</InTheWild>

<InterviewLens>
"How would you structure a service so business logic is testable and infrastructure is replaceable?" A strong answer describes ports owned by the core, driving and driven adapters, the dependency rule enforced by modules or projects, wiring at the composition root, and the judgment to use it only where the domain is rich enough to justify it.
</InterviewLens>

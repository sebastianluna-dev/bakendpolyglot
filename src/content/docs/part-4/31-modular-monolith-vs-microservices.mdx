With bounded contexts drawn, the next question is physical: one deployable or many? The industry swung from monoliths to microservices and part of the way back. The useful answer is neither fashion: get the **boundaries** right inside one process first, and pay for a network boundary only where it buys something specific. Parcel is a deliberate exception, split into five services in five languages because that is what this book is teaching; this chapter explains what that costs.

| | Modular monolith | Microservices |
| --- | --- | --- |
| Deploy | One artefact | One per service |
| Calls between contexts | In-process function calls | Network: HTTP, gRPC, messages |
| Transactions across contexts | Possible (avoid relying on it) | Not available: sagas, outbox |
| Failure | Whole process up or down | Partial failures, timeouts, retries |
| Scaling | Scale everything together | Scale each service separately |
| Team autonomy | Shared release train | Independent releases |
| Operational cost | Low | High: CI/CD, observability, platform per service |
| Refactoring a boundary | Move code, run the tests | Change contracts, migrate data |

## The modular monolith

A **modular monolith** is one deployable whose modules follow the rules services would: each module owns its tables, exposes a small public API (ports, events), and never reaches into another module’s internals or data. Every stack has a way to enforce that, and enforcement is what separates a modular monolith from the tangled kind:

| Stack | How boundaries are enforced |
| --- | --- |
| TypeScript | Nest modules exporting only their public providers; dependency-cruiser rules in CI |
| C# | One project per module; `internal` by default; references only to other modules’ contracts |
| Java / Kotlin | Spring Modulith (verifies module dependencies in a test); Java modules or ArchUnit |
| Go | `internal/` packages: the compiler forbids imports from outside the parent |
| Python | Django apps plus import-linter contracts in CI |

Modules can still publish events to each other in-process. When a module later becomes a service, the events move to a broker and the calls become HTTP or gRPC, but the boundary, and most of the code, stays the same.

## When services pay off

Extract a module into a service when at least one of these is true, and you can say which:

- **Independent scaling**: it needs ten times the resources of everything else (search, image processing).
- **Independent deployment**: a separate team must ship it on its own schedule.
- **Failure isolation**: its failure must not take down the rest (payments vs. recommendations).
- **Different technology**: it genuinely needs another runtime (an ML model in Python, a high-throughput component in Go).
- **Security or compliance boundary**: card data, health data.

Each service then needs its own CI/CD, observability, on-call, data, API versioning and contract tests. That platform cost is fixed per service, which is why small teams with many services drown.

<Pitfall title="The distributed monolith">
Services that share a database, call each other synchronously in long chains for every request, or must be released together have every cost of microservices and none of the benefits. If changing one feature always means deploying three services, the boundaries are wrong; merge them back or redraw them.
</Pitfall>

## Data ownership

The rule that makes services independent: **each service owns its data**. Other services never read its tables; they call its API or keep their own copy updated from its events. Ordering does not join to Catalog’s `products` table; it stores the product name and price it accepted at order time, which is also what the business wants (prices change, orders do not).

## Getting there: the strangler fig

Existing systems are not rewritten in one go. The **strangler fig** pattern puts a routing layer in front of the old system and moves one capability at a time to a new module or service, routing its traffic over when ready, until the old system has nothing left to do. Each step is small, reversible and delivers value.

<InTheWild>
Many well-known companies run large, successful monoliths, and several publicly moved parts of their microservice estates back into fewer services. The consensus among experienced architects: start with a well-modularised monolith, split for concrete reasons, and align services with teams. Parcel is split for teaching; in a real five-person team it would start as one modular application.
</InTheWild>

<InterviewLens>
"Monolith or microservices for a new product?" A strong answer: a modular monolith first, with bounded contexts as enforced modules and data owned per module, because the domain is still being learned and refactoring is cheap in one process; then extract services for specific reasons (scaling, team autonomy, isolation, technology), with the platform investments that each one requires.
</InterviewLens>

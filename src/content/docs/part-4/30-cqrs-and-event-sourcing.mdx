The order aggregate from Chapter 29 is shaped to enforce rules. The "My orders" page wants something else: orders with product names, shipping status and payment state, sorted and filtered, joined from several contexts. Squeezing both needs into one model makes both worse. **CQRS** separates them. **Event sourcing** goes further and stores the history of changes as the source of truth. Both are powerful, and both are frequently applied where they do not belong, so this chapter is as much about when as about how.

## CQRS

**Command Query Responsibility Segregation** splits an application into two paths:

- **Commands** change state: `PlaceOrder`, `CancelOrder`. They load an aggregate, call its methods, save it. They return little: an id, a version, or nothing.
- **Queries** read state: `GetOrderSummary`, `ListMyOrders`. They never change anything, and they read from models shaped for each screen.

CQRS does not require two databases or events. The lightest version is two code paths over one database: commands use the ORM and aggregates; queries use SQL or projections into DTOs, as in Chapter 15. That alone simplifies most services. The heavier version keeps read models in separate tables or stores (a search index, a denormalised view) updated by **projections** that consume events, which brings **eventual consistency** between write and read.

<Pitfall title="Reading your own writes">
With asynchronous projections, a user who just placed an order may not see it in "My orders" for a moment. Return the data the screen needs from the command, update the view synchronously in the same transaction for that user’s own data, or show an explicit pending state. Never let it look like the order vanished.
</Pitfall>

## Event sourcing

In a normal system, the database stores current state and history is lost unless you add audit tables. **Event sourcing** stores the history instead: every change is an immutable event appended to the aggregate’s stream, and current state is computed by replaying them.

```text
order-77  v1  OrderCreated      { customerId: c_12 }
order-77  v2  LineAdded         { sku: "BK-1", qty: 2, unitPrice: 18.00 EUR }
order-77  v3  LineAdded         { sku: "BK-9", qty: 1, unitPrice: 24.00 EUR }
order-77  v4  OrderPlaced       { total: 60.00 EUR }
order-77  v5  PaymentCaptured   { ref: "pay_31" }
```

Appending checks the expected version, which is optimistic locking (Chapter 23) for free: if two commands load version 4, only one can append version 5.

Rebuilding state is a **fold**: start from an empty state and apply each event.

const apply = (s: OrderState, e: OrderEvent): OrderState => {
  switch (e.type) {
    case 'OrderCreated':    return { ...s, id: e.orderId, status: 'draft', lines: [] };
    case 'LineAdded':       return { ...s, lines: [...s.lines, e.line] };
    case 'OrderPlaced':     return { ...s, status: 'placed' };
    case 'PaymentCaptured': return { ...s, status: 'paid' };
  }
};
const state = events.reduce(apply, emptyOrder);

fun OrderState.apply(e: OrderEvent): OrderState = when (e) {
    is OrderCreated    -> copy(id = e.orderId, status = OrderStatus.DRAFT)
    is LineAdded       -> copy(lines = lines + e.line)
    is OrderPlaced     -> copy(status = OrderStatus.PLACED)

<Stack id="go" lib="Go">
```go
func apply(s OrderState, e Event) OrderState {
	switch e := e.(type) {
	case OrderCreated:
		s.ID, s.Status = e.OrderID, Draft
	case LineAdded:
		s.Lines = append(s.Lines, e.Line)
	case OrderPlaced:
		s.Status = Placed
	case PaymentCaptured:
		s.Status = Paid
	}
	return s
}

state := OrderState{}
for _, e := range events {
	state = apply(state, e)
}
```
</Stack>

def apply(s: OrderState, e: OrderEvent) -> OrderState:
    match e:
        case OrderCreated(order_id=oid):  return replace(s, id=oid, status="draft")
        case LineAdded(line=line):        return replace(s, lines=[*s.lines, line])
        case OrderPlaced():               return replace(s, status="placed")
        case PaymentCaptured():           return replace(s, status="paid")

Every language here has a natural way to write this: a reducer in TypeScript, switch expressions over records in C#, `when` over sealed classes in Kotlin, a type switch in Go, `match` in Python. Long streams use **snapshots**: save the state at version N and replay only later events.

## When to use which

| Need | Use |
| --- | --- |
| Reads and writes have different shapes | CQRS-lite: separate query code over the same database |
| Heavy read traffic, search, cross-context views | CQRS with projected read models |
| Full audit history is a business requirement (money, compliance) | Event sourcing for that aggregate |
| "What was the state on 3 March?" queries | Event sourcing |
| Ordinary CRUD | Neither |

Event sourcing has real costs: events are a permanent public schema inside your system (you version them, never edit them), projections must be rebuildable, and every developer must learn the model. Apply it per aggregate where history is the product, as in a ledger, not to a whole system by default.

<InTheWild>
Banking ledgers, payment systems and logistics tracking use event sourcing because their business already thinks in events and needs the history. Parcel event-sources its payments ledger in the ASP.NET service, and keeps orders as plain state with an outbox. That mix is typical.
</InTheWild>

<InterviewLens>
"When would you use event sourcing?" A strong answer: when the history itself is valuable (audit, temporal queries, replays into new projections) for a specific aggregate, accepting the costs of event versioning, projections and eventual consistency; and not as a default architecture. It distinguishes CQRS, which is often useful on its own, from event sourcing.
</InterviewLens>
